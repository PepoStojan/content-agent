## CURRENT TRUTH

### 1. Product purpose

SEO Content Maker is a Next.js + Supabase application that runs a managed, multi-stage SEO content production pipeline for an organization's team: **Strategy Brief → Content Blueprint → Content → QA → Export**, each stage AI-assisted (Anthropic), versioned, and gated behind human approval. It is built for a small internal team with three roles (`team_lead`, `seo_manager`, `content_writer`) working across many concurrent projects ("pieces of content"), each fed by uploaded competitor/SERP research and existing-site knowledge, and constrained by a per-organization Business Profile and Brand Voice.

### 2. Current architecture

- **Framework:** Next.js 16 (App Router, Turbopack), React 19, TypeScript.
- **Backend:** Supabase (Postgres, Auth via Google OAuth, Storage, RLS as the authorization boundary).
- **UI:** Tailwind v4 + shadcn/ui (`base-nova` style), a locked Design V1 token system.
- **AI:** `@anthropic-ai/sdk` (Anthropic only — no multi-provider abstraction, D5).
- **Monitoring:** Sentry (`@sentry/nextjs`).
- **No background job runner.** Vercel Workflow was evaluated and explicitly deferred (D3); everything runs on plain Next.js Server Actions today.
- **Multi-tenant model:** `organizations` → `profiles` (role-scoped) → `projects`, enforced end-to-end by Postgres RLS, not just application logic.
- **Source of truth discipline:** all TypeScript enum/union types are derived from generated Supabase types (`lib/supabase/types.ts`, via `npx supabase gen types typescript --linked`), never hand-declared. This was a deliberate cleanup pass after several hand-typed unions silently drifted from the real DB enums.

### 6. RLS/security model

Every tenant-scoped table has RLS **enabled** (migration 13). Policies are added incrementally per phase, reusing two `SECURITY DEFINER` helper functions with fixed `search_path = public`:
- `current_organization_id()` — resolves the caller's org from `profiles`.
- `current_app_role()` — resolves the caller's role from `profiles`.
- `can_access_project(target_project_id)` — true if the project's org matches the caller's org, and either the caller is `team_lead`/`seo_manager` or is listed in `project_members`.

Standard policy shape per table: SELECT via `can_access_project(project_id)` (or an equivalent org/membership check for org-level tables); INSERT/UPDATE gated to `current_app_role() in ('team_lead','seo_manager')`.

### 9. Generation state machine

Defined in `lib/generation/state-machine.ts`, backed by the `generation_state` Postgres enum (15 values) and `generation_stage` enum (5 values: `strategy`/`blueprint`/`content`/`qa`/`export` — deliberately excludes `draft`, since nothing generates during draft).

- Linear happy-path: `draft → strategy_pending → strategy_generating → strategy_completed → blueprint_pending → ... → export_completed`.
- Any `*_generating`/`*_running` state can transition to `failed`.
- `failed` can only re-enter at a stage's own `*_pending` state (manual retry decision, never automatic).
- `eventStageForTransition(from, to)` resolves the correct `generation_events.stage` value for a transition into `failed` by looking at `from` (fixed a real bug where this was previously hardcoded to `"draft"`, an invalid value for `generation_stage`, causing a live 500 error).
- `transitionGenerationState()` (`lib/generation/actions.ts`) is the single write path: validates the transition via `canTransition()`, updates `projects.generation_state`, and inserts a `generation_events` row (timeline log, separate concept from `generation_runs` — see D1/D7 doc §1's "Challenge" note: `generation_runs` is the per-attempt job record with cost/telemetry, `generation_events` is the pipeline timeline, including non-generation events like a human clicking Approve).

### 10. Generation Engine

`lib/generation/engine.ts` (Phase 4.2 skeleton) — manages `generation_runs` rows only, with **zero knowledge of what a Strategy Brief/Blueprint/etc. actually is**. Current exported functions, exact as shipped in `1483bd3`:

- `startGeneration({ projectId, type, inputRef?, retryOfGenerationRun? })` — inserts a `running` row; the partial unique index (D2) is the actual duplicate guard, this function just turns the resulting `23505` constraint violation into a clean `{ status: "already_active" }` result instead of a raw error.
- `completeGeneration({ generationRunId, projectId, telemetry, outputRef?, metadata? })` — **currently a single call that sets `provider_completed_at`/`artifact_persisted_at`/`completed_at` all to the same timestamp in one update.** The function's own doc comment says this is "correct for the skeleton, where no artifact is actually being written yet" and that a real stage needing to persist a version row *between* receiving the provider response and finishing would need to call it in two steps instead — **this has not been built yet and is a known required change for the next phase** (see NEXT ACTION).
- `failGeneration({ generationRunId, projectId, error, telemetry? })` — sets `status='failed'`, `error` jsonb, partial telemetry if available, `completed_at`/`duration_ms`.
- `recoverGeneration(generationRunId)` — inspects an interrupted run and repairs it without ever recalling the provider: `artifact_persisted` → mechanically flips to `completed`; `provider_completed` → returns `needs_persist` (does not attempt to persist itself — stage-specific, deliberately out of the engine's scope); `queued`/`running` with no `output_ref` → marked `failed`, retryable; already-terminal → no-op.

All four functions are role-gated via `assertCanRunGenerations()` (`team_lead`/`seo_manager` only).

## LOCKED DECISIONS

(Architecture and process rules established and reaffirmed across the session — not subject to casual relitigation.)

- **Versioned artifacts, head+version pattern.** Every generated artifact (Brief, Blueprint, Content, etc.) has a head table (e.g. `content_briefs`) with a `current_version_id` pointer, and an immutable, append-only versions table. Nothing is ever overwritten or deleted; regeneration always inserts a new version and moves the pointer.
- **Approval gates + provenance labeling.** A single global strict-approval-gate model. Every field in generated artifacts must be labeled as one of: Research finding (immutable, sourced from `research_sources`), AI recommendation (editable, Claude's synthesis), User decision, or System validation. This distinction is not cosmetic — it determines which app code is allowed to write which field (see `brief_topics` vs `brief_versions.entities_concepts` in the Phase 4.3 plan).
- **AI provider:** Anthropic only, no abstraction layer beyond the stage function itself (D5).
- **Prompts are file-based, never DB-stored** (D4).
- **No background job runner** (Vercel Workflow explicitly deferred, D3) — plain Server Actions.
- **RLS is the real authorization boundary, not UI state.** Explicitly relearned twice in this project (disabled buttons are not security; hidden UI elements are not security) — every table gets real Postgres policies, not just app-level role checks.
- **All new/changed RLS helper functions must be `SECURITY DEFINER` with `SET search_path = public` from day one** — mandatory pattern after the Phase 3 recursion bug (§20).
- **Migrations are strictly additive.** Never edit an applied migration; always create a new file.
- **TypeScript enum/union types are always derived from generated Supabase types**, never hand-declared duplicates of a Postgres enum.
- **Never print, commit, log, expose, or include the Anthropic API key in source code or diagnostic output**, in any phase from Phase 4.3 onward. Key lives in `.env.local` only.

## 20. Critical lessons / root-cause findings from previous debugging

Preserved verbatim in intent from the migrations' own comments — these are hard-won, not generic advice:

1. **RLS recursion bug (`can_access_project`).** Root cause: `can_access_project()` ran as `SECURITY INVOKER` while also being the `USING` expression of `projects_select_accessible` on the very table it queried. `ensureDraftProject()`'s `.insert(...).select("id")` forced a RETURNING-clause SELECT-policy check on the new row, which called `can_access_project()`, which queried `projects` again under the same policy — a recursive, RLS-governed self-reference. This produced the exact same error text as a `WITH CHECK` failure ("new row violates row-level security policy for table projects") even though the INSERT's own `WITH CHECK` was passing — a genuine footgun for diagnosis, since the error message pointed at the wrong clause. Every other hypothesis (identity/value mismatch, the policy itself, missing triggers, `profiles`' own RLS) was ruled out first. Fix: `SECURITY DEFINER` + fixed `search_path` + schema-qualified references, so internal queries bypass RLS re-evaluation instead of recursing.
2. **The same root cause class hit `current_organization_id()`/`current_app_role()` first**, one migration earlier — as plain functions with no fixed `search_path`, their internal query against `profiles` ran under the caller's privileges/search_path at evaluation time *inside another table's RLS policy check*, resolving inconsistently from how they resolved when called directly.
3. **Postgres will not let you use a newly-added enum value inside an index predicate in the same transaction it was added in** (SQLSTATE 55P04) — forced splitting the Phase 4.2 migration into an enum/columns file and a separate index file.
4. **`Database = any` placeholder types hid several real bugs at compile time.** Regenerating real types via `supabase gen types typescript --linked` (works without the DB password) immediately surfaced multiple hand-typed-union drifts from the real DB enums — fixed by deriving every such type from `Database["public"]["Enums"][...]` instead.
5. **A `redirect()` call inside a Server Action can be caught by a client-side try/catch and shown to the user as an error** (`NEXT_REDIRECT`) — fixed using `unstable_rethrow(e)` from `next/navigation` at the top of the catch, per Next.js's documented pattern for this footgun.
6. **A file input's `.files` read from a ref at a later event (e.g. click-time) can return `undefined`** even though a file is visibly selected — fixed by capturing the file immediately in `onChange` via `useState<File | null>`, not reading a ref later.
7. **Renaming an enum value cascades silently.** Renaming `generation_run_status`'s `succeeded`→`completed` broke `lib/generation/actions.ts`, which reused that same enum for `generation_events.status` with a hardcoded `"succeeded"` string literal — caught only by re-reading the file, not by any type error (the literal was still a valid string at the time). Lesson: grep for every literal use of an enum value before renaming it in a migration.

- **QD4 (cost control):** exactly 2 LLM calls per QA run, flat regardless of document length — one whole-document `intent` call, one batched `factual` call covering every evaluated leaf section in one structured response. Directly closes Phase 4.2's own flagged, previously-unaddressed risk #4 ("AI QA re-run cost... no cooldown or guard").
- **QD5 (immutability):** a QA report is an insert-only snapshot; "Re-run validation" always creates a brand-new `qa_reports` row. No per-finding/per-category re-run or dismiss/override in this phase — the only correction path is fix-the-content-then-re-run-whole-report.
- **QD6 (staleness, includes a lock-time clarification):** a QA report is stale when the exact content-version set it evaluated no longer matches current for any evaluated leaf, **and** also stale if the Blueprint's structure/version has changed in a way that changes the evaluated leaf set itself (a leaf added/removed/restructured since the report ran — content-version comparison alone can't catch this case). A stale report must not satisfy Export's QA-blocking rule. Stale reports are never auto-deleted.
- **QD7 (anti-hallucination):** every LLM-sourced finding above PASS must carry a literal, locatable quoted excerpt from the actual evaluated text; a finding whose quote doesn't resolve to real text is rejected before persistence, not stored.
- **QD8 (telemetry):** one `generation_runs` row per `qa_reports` row (`type='qa_run'`, already in the enum, no schema change), both LLM calls' token usage summed into that row's totals, per-call usage kept in `metadata` for audit.

**Evidence-awareness rules (locked, cross-cutting):** QA is evidence-aware, not evidence-blind — `factual` QA is always given the section's own supplied evidence as context. It receives the exact same relevance-filtered evidence packet (Phase 4.5 CD2's deterministic, capped `research_sources` subset, recomputed fresh) the writer had access to for that section — never a wider or re-imagined set. QA must not evaluate claims against external/model knowledge that wasn't supplied to the system — a claim the model merely knows to be plausible from training data, with nothing in the supplied evidence to back it, is treated as insufficient evidence, not waved through. QA must not invent findings — every finding above PASS requires a real, locatable quote (QD7), never an unattached assertion.

## Toyota Performance Principle

Engineering rules for any future performance work on this project. Recorded now, before any new performance architecture changes are made — not a redesign, a set of standing constraints for how performance work gets done here.

- Measure before optimizing.
- Avoid unnecessary DB queries.
- Avoid duplicate data fetching.
- Parallelize independent server reads where it materially reduces latency.
- Compute deterministic values once and reuse them.
- Never use AI for deterministic work.
- Keep AI calls minimal and bounded.
- Keep section context small and relevance-filtered.
- Avoid heavyweight UI dependencies.
- Avoid creating duplicate sources of truth.
- Track latency/token usage on major AI operations.
- Optimize measured bottlenecks rather than prematurely optimizing everything.

## Session — 2026-08-20 (LEAVES-03): Full QA / Partial QA / No QA — clarified as three distinct states, proposed QD9 + ED13, NOT locked

Real use of the shipped QA pipeline surfaced a distinction ED12 alone doesn't capture: "no verified QA" and "some QA, deliberately narrower in scope" are not the same thing, and conflating them either overcharges a user who only wanted a cheap, targeted check, or risks a genuinely-incomplete result being read as a full pass. This session analyzed and proposed architecture for three distinct states — **Full QA**, **Partial QA** (new), and **No QA / Export without QA** (ED12, unchanged) — without writing code, migrations, or making Anthropic calls, per the task's own constraint. **Nothing below is locked.**

**QD9 (proposed, `docs/architecture/phase-4-6-qa-plan.md`) — Partial QA, a user-selected subset of the 9 categories, chosen before a QA run:**
- A run accepts an optional non-empty `selectedCategories`; omitting it means all 9 (full QA stays the literal, unchanged default). Every run — full or partial — still produces one new, immutable `qa_reports` row (QD5 unchanged); no report is ever edited to hide a FAIL, unchanged RLS enforcement.
- A skipped category gets **zero `qa_findings` rows** — never a synthetic "N/A" finding, never silently reusing an old report. Explicitly **not** derivable from "which categories have zero findings" — this project's own QA backend already produced a real case (`factual` against a thin project) where an *evaluated* category legitimately had zero findings, which is exactly why evaluated/skipped sets must be stored, not inferred.
- **Schema gap identified, no migration created:** `qa_reports` needs two new columns, `evaluated_categories qa_category[]` and `skipped_categories qa_category[]`, both populated once at report-creation time, both explicitly persisted (not just one derived as the other's complement) — future-proofed against the frozen 9-category set itself ever changing. `qa_findings` needs no change.
- **Real cost saving, not just a display filter:** selecting only deterministic categories triggers **zero** Anthropic calls — QD4's "exactly 2 LLM calls" becomes "0, 1, or 2 depending on selection."
- **How it differs from ED12 (requirement D, answered explicitly):** ED12 is a human **overriding** the QA verdict (or its absence) at export time, always resulting in `qa_bypassed = true` and an Unverified export. QD9 is the QA system's own verdict being **followed**, just over a smaller, honestly-labeled scope, chosen before the run exists — a QD9 report that itself FAILs or goes stale still only becomes exportable via ED12's unchanged bypass path; QD9 never softens ED12's bar.

**ED13 (proposed, `docs/architecture/phase-4-7-export-plan.md`) — three Export provenance tiers, consuming QD9, extending ED2's gate output (not its mechanism):**
- **Verified** (full report, current, not FAIL, `qa_bypassed = false`) — unchanged from today's normal export.
- **Partially verified** (partial report, current, not FAIL among evaluated categories, `qa_bypassed = false`) — new: Allowed through the *normal* Export button, gated by one lightweight, mandatory acknowledgment naming the skipped categories (deliberately lighter than ED12's override-confirmation, since no gate is being overridden — the checked categories genuinely passed).
- **Unverified** (`qa_bypassed = true`, ED12, unchanged) — no report, stale report, or FAILing report (full or partial), all funneled through the one unchanged ED12 bypass action.
- **No new stored column proposed** — the tier is computed from `qa_report_id` (ED1) + `qa_bypassed` (ED12) + the joined report's `skipped_categories` (QD9), all already-immutable once written; storing it a third time would duplicate a source of truth this project has been careful to avoid elsewhere.
- **Metadata, extending ED12's existing per-format convention unchanged in mechanism:** Structured JSON's `qaState` gains `evaluatedCategories`/`skippedCategories` arrays; Markdown/HTML/DOCX get a third one-line metadata-only variant ("Export status: Partially verified — N of 9 categories evaluated") alongside ED12's existing Verified-is-silent / Unverified wording — no publishable body content altered in any tier.

**Companion QA-tab UI proposal (`docs/architecture/phase-4-6-qa-ui-plan.md`):** a "Customize…" action alongside the existing Run/Re-run QA button, opening a 9-category checklist (all checked by default); category cards gain a fourth "Not evaluated" state, visually distinct from a legitimate zero-findings PASS (flagged as the single easiest place this proposal could accidentally reintroduce the exact ambiguity it exists to prevent); the report banner gains a "Partial QA — N of 9 evaluated" line whenever the latest report isn't full, with no such line on a full report.

**Safety framing, restated as the constraint governing all three documents' new sections:** a partial report must never render, compute, or be mistaken as a full QA pass anywhere — not in `overall_status`'s meaning, not in the QA tab, not in an exported file's metadata. A skipped category has no finding, no status, and is always shown as an explicit "Not evaluated" state, never omitted and never implicitly PASS.

**Status: all of QD9/ED13/the Customize-QA UI proposal are explicitly NOT locked** — proposed architecture only, recorded precisely enough for a future review to lock or amend without re-deriving the analysis, per this task's own instruction. No code, no migrations, no Anthropic calls made producing this analysis. No commit made.

**Review complete — QD9, ED13, and the Customize-QA UI proposal are now locked (LEAVES-04, below), with one required amendment to QD4.**
