This document designs that tab, plus the Export tab's gating logic (Export's own tab is *also* still hardcoded locked and has no UI at all — this document defines only the QA-gating rule Export must consume, not Export's own screen, which remains Phase 4.7's job per the existing Export schema's own untouched status).

## 1. Overall result (requirement 1)

A single banner at the top of the QA tab, matching the exact visual shape Brief/Blueprint's own approval banners already use (`rounded-[10px] border ... px-4 py-3`, tone-matched):

- **PASS** (`tone="success"`): "All checks passed. Ready to export." — a direct link to the Export tab (once it exists) sits here, not duplicated elsewhere.
- **WARN** (`tone="warning"`): "No blocking issues. N warning(s) worth reviewing before export." — Export remains allowed (§6); this is a nudge, not a gate.
- **FAIL** (`tone="danger"`): "N finding(s) must be resolved before you can export." — the banner itself does not list every FAIL (that's the category cards' job, §2); it states the count and points down the page.

The banner is always the single source of truth for "what should I do next" (requirement 7) — every other piece of UI (category cards, individual findings) is detail underneath it, never a competing headline.

## 2. Category-level results (requirement 2, QU1/QU2)

Nine category cards, one row each, fixed order (QD3's own order: `topics`, `entities`, `structure`, `links`, `brand`, `style`, `forbidden_chars`, `intent`, `factual`) — never re-sorted by severity or alphabetically, so a user learns a stable layout across runs. Each card, collapsed by default, shows: category name, its `ProvenanceBadge` (`system` for the 7 deterministic categories, `ai` for `intent`/`factual` — a categorization fact, not a per-finding toggle), its rolled-up `StatusBadge` (QU2), and a finding count. Clicking expands the card in place to list its individual findings — no navigation, no re-fetch (every finding for every category was already loaded in the one `qa_findings` query, QU9).

A category with zero findings (possible today — e.g. `factual` when zero sections have content, exactly the real execution already observed) renders as **PASS with an explicit "nothing to evaluate" note**, never silently omitted — an omitted category would look like a gap in the report rather than an honest "there was nothing here to check."

## 3. Finding details (requirement 3, QU3)

Each expanded finding shows, in a fixed layout:

- **Severity** — `StatusBadge` (`success`/`warning`/`danger`), same visual language as the category rollup, not a separate scheme.
- **Category** — already established by the parent card; not repeated per-finding, avoiding redundant visual noise.
- **Affected section** — the section's title (resolved via `content_version_id → blueprint_node_id → title`, reusing the Content Editor's own already-fetched lookup, QU9), or "Whole document" for the whole-document findings (`structure`'s leaf-coverage summary, `style`'s cross-section repetition check, `intent`) — `content_version_id: null` is the exact signal for this, already how the backend distinguishes it (QD1).
- **`content_version_id`** — shown small, monospace, muted (`font-mono text-[11px] text-text-muted`), the same treatment every other technical id already gets in this app (Blueprint node ids, generation run ids) — present for audit/reproducibility, not a headline.
- **Explanation** — the finding's `note`. **Confirmed gap (QU3):** for LLM findings, this currently also contains the literal quote baked into the same string (`generate-qa-report.ts`'s `validateLlmFinding`) rather than a separate field — the UI, as specified by this plan, would show the quote embedded in the explanation text rather than as its own labeled element until that backend gap is closed. Flagged, not solved here.
- **Evidence/reference** — for deterministic findings, the note text itself already states the mechanical reason (e.g., "3/4 title terms are present," "None of this section's assigned entities appear"); no separate evidence field exists or is needed. For `factual`, "evidence" in the sense of *which research sources the section was evaluated against* is not currently surfaced to the found finding at all (the LLM call saw it, QD-plan's evidence-awareness rules, but the persisted `qa_findings` row doesn't carry a reference back to which `research_source` ids were in scope) — a second, smaller instance of the same class of gap as QU3, flagged the same way, not solved here.
- **Suggested action** — UI-derived text, never stored: a FAIL/WARN with a `content_version_id` reads "Edit or regenerate '[section title]' to address this" with the §4 navigation link; a whole-document finding (`content_version_id: null`) reads "Review the whole document" with no single-section link (there is nowhere more specific to send the user). A PASS finding shows no suggested action at all — nothing to do.

## 4. Navigation to the affected section (requirement 4, QU4/QU5)

**Real, required plumbing this plan surfaces precisely (not built here):** `ProjectTabs` currently has no mechanism for one tab to control another's internal state. The minimal fix: `ProjectTabs` adds one more piece of state, `pendingContentSelection: string | null` (a `blueprintNodeId`), alongside its existing `tab` state. A QA finding's "Go to section" button calls a callback (passed down through the QA tab's props, mirroring how `onSelect`/`onApprove` etc. are already threaded through every other tab) that sets `pendingContentSelection` and switches `tab` to `"content"` in one action. `ContentEditor` gains one new optional prop, `initialSelectedSectionId`, consumed once (an effect or lazy `useState` initializer, implementation's choice) to override its own default first-section selection — its existing internal `selectedId` state and all existing interaction logic (Edit/Regenerate/Approve) are otherwise completely untouched.

**Degrades honestly when the section no longer exists in the current Blueprint (QU5):** because a stale QA report can reference a `content_version_id` whose `blueprint_node_id` isn't a leaf of the *current* Blueprint version (the exact BD6 scenario proven live twice already this phase), "Go to section" must check the target id against the Content Editor's own current section list *before* offering to navigate. If absent, the button is disabled with an explicit reason ("This section is no longer part of the current Blueprint version — see Blueprint version history") rather than either silently failing or navigating to the wrong/nonexistent section. This check is free — it's a lookup against data already being fetched for the Content Editor tab regardless (QU9), not a new query.

## 5. Staleness (requirement 5, QU6)

Three states, visually and textually distinct, never conflated:

| State | Trigger | Visual treatment | Primary action |
|---|---|---|---|
| **No QA run** | No `qa_reports` row exists for the project | Neutral empty-state card, same tone as Content Editor's "No Content generated yet." (BD6 precedent) | "Run QA" (primary button) |
| **Current QA** | Latest report's evaluated content-version set *and* leaf-set both match the project's current state exactly (QD6) | Full-color banner per `overall_status` (§1), category cards shown normally | Context-dependent (§1) |
| **Stale QA** | Latest report exists but fails either staleness check (QD6 — content edited/regenerated, or Blueprint version/leaf-set changed since the report ran) | The *same* findings are still shown (historical value — QD6 never says delete a stale report) but wrapped in a distinct muted/amber "This QA result is out of date" banner **above** the normal report, de-emphasizing (not hiding) the color-coded category cards underneath | "Re-run validation" (primary, visually emphasized over any other action on the page) |

Staleness detection reuses data, per QU9 — it does not add a comparison the backend hasn't already defined (QD6's own two checks, restated verbatim here as UI logic, not redesigned).

## 6. Export gating (requirement 6, QU7)

Exactly four states, one deterministic function, never computed two different ways in two different places:

1. **Allowed** — latest `qa_reports` exists, is not stale (§5's "Current QA" state), and `overall_status !== 'fail'` (PASS or WARN both allow Export — only FAIL blocks, per Design V1 rule 8's literal wording: "Export is blocked while any QA category is FAIL," not "while any category isn't PASS").
2. **Blocked — FAIL** — latest QA is current (not stale) and `overall_status === 'fail'`. Export tab (once built, Phase 4.7) shows exactly which categories are FAIL, linking back to the QA tab's category cards rather than duplicating finding detail.
3. **Blocked — stale** — latest QA exists but fails either staleness check (§5). Treated identically to "no QA," per QD6's own locked wording ("treat a stale report... the same as no report for gating purposes") — a stale PASS must never be read as permission to export.
4. **Blocked — no QA** — no `qa_reports` row exists at all.

This document defines only the gating **rule** — the Export tab's own screen, its format-selection UI, and its unlock precondition relative to `projects.status` are explicitly Phase 4.7's job and are not designed further here (the Export schema exists, untouched, RLS-enabled-zero-policies, exactly as Phase 0 left it — same "flag the gap for its own future phase" treatment already given to Export throughout this project's history).

## 7. Human workflow (requirement 7)

The design deliberately keeps one thing always true: **the banner at the top of the page (§1) is the single most important sentence on the screen, and it always states the next action.** No QA yet → "Run QA." FAIL → "N finding(s) must be resolved" with the count matching exactly what's expandable below. WARN-only → "no blocking issues," Export already reachable. PASS → "ready to export," with a direct link. Stale → "out of date, re-run" is the loudest thing on the page, overriding even a stale PASS's would-be reassuring green. A user should never need to read every category card to know what to do next — only to understand *why*, if they choose to.

## 8. Explicitly rejected (requirement 8, QU8)

- **Per-finding dismiss** — rejected, matches QD5 exactly (no per-finding resolution state exists or is proposed; the only correction path is fix-the-content-then-re-run-whole-report).
- **Per-finding or per-category re-run** — rejected, matches QD5 exactly (whole-report re-run only).
- **A numeric AI quality score** — rejected, matches Design V1 rule 6 exactly ("no single blended SEO score... category-level PASS/WARN/FAIL only"). No aggregate percentage, no letter grade, no progress bar implying a continuous scale — the nine category badges are the entire summary.
- **Auto-fixing** — rejected; never designed anywhere in this pipeline (Phase 4.6's plan itself: "QA never approves anything," it diagnoses, a human acts). Not opened by this document.

## 9. Efficiency (requirement 9, QU9)

Three queries, flat regardless of document size: (1) latest `qa_reports` row (`ORDER BY run_at DESC LIMIT 1`), (2) all `qa_findings` for that report (one `WHERE qa_report_id = X`, no per-category or per-finding fetch), (3) `qa_report_content_versions` for that report (staleness comparison only). Section-title lookups and leaf-set staleness comparison reuse the Blueprint tab's node list and the Content Editor tab's `content_documents`/`content_versions` mapping — both already computed by `page.tsx` for their own tabs on every page load regardless of whether QA is even visited; the QA tab adds zero duplicate fetching of that data. Category rollups (QU2) are computed in memory from the small `qa_findings` array already in hand — no additional query. The default rendered view is compact (9 one-line category rows); individual findings are a client-side expand/collapse over data already present in the page's initial payload, never a second network round-trip.

## 10. Design V1 (requirement 10, QU10)

Zero new components. `Card` for every card-shaped surface (category rows, the banner, the empty state) — same 16px radius, 1px border, no drop shadow discipline as everywhere else. `StatusBadge` for every PASS/WARN/FAIL, at both the overall and category level — the `danger` tone (already defined, unused elsewhere yet, confirmed present in `status-badge.tsx`) is QA's first real consumer. `ProvenanceBadge` with `source="system"` for the 7 deterministic categories and `source="ai"` for `intent`/`factual` — this is precisely the categorization Design V1's own README already specifies for QA ("System validation: neutral badge next to QA/validation panels; PASS/WARN/FAIL use green/yellow/red per above"), not a new interpretation. No chart, gauge, sparkline, or percentage ring anywhere — the explicit "workbench, not a management dashboard" framing rules out anything that visually implies a continuous score, reinforcing QU8's rejection of a numeric quality score at the component level, not just the data level.

## "Customize QA" UI for Partial QA (QU11, locked 2026-08-20, LEAVES-04)

**Status: locked UI architecture, extending the already-implemented QA tab. Not yet implemented.** Raised as a proposal during LEAVES-03, companion to `docs/architecture/phase-4-6-qa-plan.md`'s QD9 (partial/user-selected-category QA runs); reviewed and **locked, without amendment, as QU11** during LEAVES-04, kept in this document because it's the natural home for QA-tab UX per this doc's own scope.

**G. Run entry point — two explicit paths, not a hidden option.** The existing single "Run QA"/"Re-run validation" action (§1, §6, unchanged as the default) gains a sibling secondary action, **"Customize…"**, opening a lightweight checklist of the 9 fixed-order categories (same order as the category cards themselves, §1) grouped exactly as they already visually group in Design V1 — deterministic (`topics`/`entities`/`structure`/`links`/`brand`/`style`/`forbidden_chars`) vs. AI (`intent`/`factual`) — each with a checkbox, all checked by default (so "Customize" defaults to visually equivalent to "Run full QA," and unchecking is the actual customization gesture, not an empty-state the user has to build up from scratch). A "Run selected" button is disabled when zero categories are checked (mirrors the Export tab's own "disabled unless ≥1 format checked" pattern, `phase-4-7-export-plan.md` §9) — the real, server-side-enforced floor (QD9's own "zero-category run is rejected server-side") is backed by this UI courtesy, not replaced by it.

**Report-level Full/Partial label.** The banner (§1, unchanged in every other respect) gains one additional line whenever the *latest* report is partial: **"Partial QA — N of 9 categories evaluated"**, naming the skipped categories inline (matching the same directness already used for individual finding text, e.g. QD7's quote requirement). A full report shows no such line — the absence of the label is itself the honest "this was complete" signal, avoiding a redundant "Full QA" badge that would just be noise on every ordinary report.

**Category cards — a fourth state, locked exact copy.** Today's category cards render exactly one of PASS/WARN/FAIL (§1, QU2's rollup). This adds a fourth, visually distinct **NOT EVALUATED** state (neutral tone, matching `StatusBadge`'s existing `neutral` variant — no new component) for any category present in the latest report's `skipped_categories` (QD9's schema). Locked copy, deliberately short and unmistakable: **PASS renders "Nothing found"; NOT EVALUATED renders "This category was skipped."** These two must never be visually or textually confusable — a legitimate zero-findings PASS ("Nothing found") means the category was checked and nothing was wrong; NOT EVALUATED ("This category was skipped") means it was never checked at all. **All 9 categories are still always shown, in the same fixed order, every time** (QU1's own discipline, unchanged) — a skipped category is never omitted from the list, only labeled differently; omitting it would be exactly the "silently treat skipped categories as PASS" failure mode requirement H prohibits, just by a different mechanism (disappearing instead of mislabeling). NOT EVALUATED cards are not expandable (there is nothing to expand — zero findings, by design, QD9 §B).

**Interaction with staleness/no-QA (§5, §6 — unchanged mechanisms, extended labeling only).** A partial report can be stale exactly like a full report (QD6, untouched by QD9) — the existing stale banner (§5) gains the same "N of 9 evaluated" qualifier so a stale-and-partial report doesn't read as merely stale-but-otherwise-complete. The no-QA empty state (§5) is unchanged — "no report" and "a report exists but skipped everything" are different, impossible states are kept impossible (QD9's own server-side non-empty-selection floor means a report can never legitimately have all 9 in `skipped_categories`).

**Why this doesn't reopen QU8's rejections.** "Customize QA" selects *which categories run*, decided once, before the run — it is not a per-finding or per-category re-run/dismiss/override of an *existing* report's findings (QU8, unchanged, still fully rejected). A user who wants different category coverage still triggers a brand-new, immutable report (QD5/QD9, unchanged) — this proposal adds a new *input* to report creation, never a new way to *edit* one after the fact.

## QA Diagnostic Context Panel — "Review issue" (QU12, LOCKED 2026-08-20, QA-11)

**Status: locked architecture (no code, no migration, no Anthropic call made producing or locking this section, matching this document's own planning-only constraint for architecture decisions before implementation) — subsequently implemented and browser-verified in QA-12.** Raised as a proposal during QA-10 (real-use finding: today's "Go to section," QU4/QU5, navigates the user to the Content Editor and selects the right section, but stops there — the user sees the section's body and is left to independently reconstruct what QA actually evaluated, what the Blueprint expected, what was and wasn't detected, and why the finding fired, often forcing a second trip back to the Blueprint tab, BD5's own inspector, to reconstruct context the QA finding already had in hand at the moment it was raised); reviewed and **locked, without amendment, as QU12** during QA-11, following the same propose-then-lock precedent already established by QD9/ED13 (LEAVES-03 → LEAVES-04) and QU11 itself.

### The redesigned action: "Go to section" → "Review issue"

The action itself is renamed conceptually (not just relabeled) from *navigate* to *review*: clicking it still switches to the Content Editor and selects the section (QU4's existing `pendingContentSelection` plumbing, unchanged, reused unmodified — no new cross-tab state mechanism is proposed), but it additionally passes the **specific finding** that was clicked (its category, status, note, quote, and `content_version_id` — all fields the QA tab already has in hand from its existing single `qa_findings` fetch, QU9, no new query) into a new, small piece of Content Editor state: `activeQaFinding: QaFindingContext | null`.

**Temporary, not persistent:** `activeQaFinding` is cleared the moment the user performs any editing action (Edit, Regenerate, Save, Cancel) or explicitly dismisses the panel — it is a one-shot diagnostic overlay for the specific finding that was clicked, not a persistent Content Editor feature or a second copy of the QA report living inside another tab (this task's own explicit "do not duplicate the entire QA report inside Content Editor" instruction). Selecting a different section through the Content Editor's own sidebar (unrelated to the finding) also clears it — the panel is scoped to "the section this finding is about," not "whatever section happens to be open."

### Panel contents (requirement 1, A–G)

A collapsible card, positioned above the existing "Blueprint context" panel (LEAVES-01, unchanged, stays separate — requirement 5's explicit instruction) and below the section header, shown only while `activeQaFinding` is set:

| Field | Source | Notes |
|---|---|---|
| **A. What QA evaluated** | `activeQaFinding.category` + its fixed label (reusing `qa-review.tsx`'s existing `CATEGORY_LABEL` map, not a new one) | e.g. "Entities" |
| **B. What was expected from the Blueprint** | The section's own `blueprintContext` (LEAVES-01, already fetched, already attached to `ContentSectionDetail` — zero new query) filtered to the fields relevant to the finding's category (§ below) | Never the whole Blueprint node dump — only the field(s) the category actually checks |
| **C. What was detected in the actual content** | Category-specific (§ below) — derived client-side from data already in hand, or read directly from the finding's own `note`/`quote` | No new backend computation; this panel never re-runs a check |
| **D. What is missing/problematic** | Category-specific (§ below) | |
| **E. Why QA raised the finding** | `activeQaFinding.note` (existing field, unchanged) | Verbatim — never reworded |
| **F. A practical suggested action** | New, UI-derived, deterministic text — never stored, never AI-generated (§ "Recommended actions" below) | |
| **G. Existing Edit / Regenerate actions** | The Content Editor's own existing buttons, completely unchanged | The panel sits alongside them, never replaces or gates them |

A **"Back to QA"** link (reverse of QU4's own navigation) and a **dismiss** control (clears `activeQaFinding` without navigating away) sit at the panel's own header — the user is never trapped in the diagnostic view.

**Two real, small, already-known gaps this table surfaces again (not new discoveries — both already flagged in `phase-4-6-qa-plan.md` §2/§3):** the `brand` category's specific triggering rule and the `factual` category's specific evidence-source references are not currently persisted anywhere a UI could read them back structurally — today's panel would fall back to `note`/`quote` text for both, which is honest and sufficient (nothing is fabricated), just not as structured as the table's ideal shape. Not solved by this proposal; flagged for the same "small additive column, future implementation pass" treatment already given to `qa_findings.quote` itself.

### Recommended actions (requirement 6)

Deterministic, template-based, UI-derived text only — **never AI-generated, never auto-applied, never an auto-fix workflow** (this task's own explicit prohibition, matching QU8's existing rejection of auto-fix):

- Entities/Topics, `none`/missing: *"Consider naturally mentioning **{term}** in this section if it's relevant to the explanation."* — one line per missing item, capped at 3 named explicitly then "+N more."
- Links: *"Consider linking to **{target title}** where relevant."* (from the section's own unused `internalLinkTargets`, if any remain unlinked)
- Brand/Forbidden characters: *"Remove or rephrase the flagged text before re-running QA."*
- Factual: *"Verify this claim against the section's supporting evidence, or soften/remove it if unsupported."*
- Intent/Structure/Style: *"Review the whole document; this finding isn't tied to one section."* (matches §3's existing whole-document suggested-action text, unchanged)

This is a direct textual template keyed on `category` + coverage shape — not a new scoring or ranking system, and not stored (computed at render time from data already in the panel).

### Explicit non-goals (requirement 6, restated as hard constraints)

- **No auto-edit** — the panel never writes to `content_versions`, directly or indirectly.
- **No auto-insert of entities/links/text** — "suggested action" is copy a human reads, never a button that mutates the body.
- **No AI auto-fix workflow** — no Anthropic call is introduced by this proposal anywhere.
- **No duplication of the full QA report inside Content Editor** — the panel shows exactly one finding's context, never a list of all findings for the section or the project; "Back to QA" is the way to see the rest.
- **No new QA category, no new scoring system** — every field above is either already-fetched data or a parse/template over an existing `note`/`quote` string.

### Efficiency (Toyota, same discipline as every other panel in this app)

Zero new queries for the common path: `activeQaFinding` is populated entirely from the QA tab's already-fetched `qa_findings` row (QU9) plus the Content Editor's already-fetched `blueprintContext` (LEAVES-01) — both exist in memory before this panel renders. The only two genuinely new reads this proposal identifies (Brand's triggering rule, Factual's evidence-source list, and Intent's Brief fields if not already fetched) are each a single small, already-scoped lookup, not a new class of query pattern, and are explicitly flagged as follow-up gaps rather than blocking this proposal.

## Key risks, ranked

1. **QU3/§3's baked-in quote is the sharpest concrete gap this pass found** — it's the one place this plan cannot fully satisfy the stated UI requirement (show quote and explanation separately) without a small backend change this document is explicitly not authorized to make. Should be the first thing addressed when implementation begins, likely as a small additive migration (`qa_findings.quote`) plus a `generate-qa-report.ts` change to stop concatenating it into `note` — both out of scope here, flagged precisely so the next pass doesn't have to rediscover it.
2. **QU4's cross-tab navigation state is real, if small, new architecture** — `ProjectTabs`/`ContentEditor` have never needed to talk to each other before; getting the "one-time consume, then behave exactly as today" contract right (so it doesn't fight the Content Editor's own existing `selectedId` state on every subsequent interaction) is worth deliberate care at implementation time, not a five-minute prop add.
3. **QU5's graceful-degradation case is easy to skip if implementation rushes navigation** — a naive "just link to `?section=<id>`" implementation would silently produce a broken or misleading link for stale findings referencing orphaned (BD6) sections; this must be checked explicitly, not assumed away.
4. **Export's own tab/unlock design remains completely undecided** — this document deliberately scoped Export down to "the gating rule QA produces" (§6) and did not design Export's screen, formats UI, or its own unlock precondition relative to `projects.status`. That gap is real and will need its own planning pass (Phase 4.7), not an afterthought bolted onto this one.
5. **A category with legitimately zero findings (`factual` when nothing has content, already observed live) must render as an honest PASS-with-explanation, not vanish** — an implementation that naturally "just doesn't render a category with no rows" would silently produce a QA report that looks incomplete rather than one that's telling the truth about an empty document. Named explicitly in §2 to prevent this from being an accidental omission.
6. **QU11's NOT EVALUATED state and a legitimate zero-findings PASS (risk 5, above) must never be visually confusable at implementation time, despite locked distinct copy.** Both can show zero findings under a category card, but they mean opposite things (one wasn't checked at all; one was checked and found nothing wrong) — the locked copy ("Nothing found" vs. "This category was skipped," above) is deliberately distinct, but tone/color/iconography must reinforce, not just the text — worth explicit side-by-side design review at implementation time, not just a copy change applied to the existing PASS card style.
