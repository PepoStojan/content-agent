# Phase 4.7 — Export: Architecture Plan

Status: **planning only (2026-08-20).** No code, no migrations, no Anthropic calls made producing this document. Grounded directly in the schema as it exists today (read from the actual migration files, not assumed): `exports`/`export_content_versions`/`export_files` (`20260817000011_export.sql`, unused since Phase 0, RLS-enabled with zero policies), `export_status` (`idle`|`running`|`done`|`failed`), `generation_run_type` (`export` already present in the enum, unused since Phase 0 — confirmed directly in `lib/supabase/types.ts`), the completed Content pipeline (`lib/generation/content/*`, CD6's computed-on-read article assembly), the completed QA pipeline (`lib/generation/qa/*`, QD6's staleness logic), and `lib/generation/blueprint/tree-order.ts`'s `orderNodesByDocumentPosition()`. This document assumes and reuses everything already proven in Phases 4.2–4.6 (the RLS migration pattern, the "flag the schema gap, don't build it here" pattern used for Blueprint's `brief_version_id`, Content's `blueprint_node_id`, and QA's `content_version_id`) rather than re-deriving it.

**Central framing, stated once and held throughout:** Export is a **deterministic downstream artifact assembler**, not an AI generation stage. It reads already-approved, already-QA'd data and transforms it into files. No prose is written, no judgment is exercised, nothing is synthesized — Export's only real risk surface is "did it faithfully reproduce what was already approved," not "did it produce good content." This reframes several questions (§8, §11) that would look different if Export were treated as "just another generation type by default."

## 0. What Export is and is not

**Is:** a deterministic transform. Input = a fixed, already-approved set of database rows (Brief version, Blueprint version + node tree, N leaf content versions). Output = files in four possible formats, each a faithful, mechanical re-rendering of the same approved text. Nothing in this pipeline stage exercises judgment, calls a model, or produces new prose.

**Is not:** a sixth AI generation stage. Every prior phase (Brief, Blueprint, Content, QA) shares one real risk shape — "did the model fabricate or misrepresent something" — and one real architecture (the three-phase Generation Engine lifecycle exists specifically to manage that risk: durably store the raw provider response before parsing, in case parsing crashes after a real dollar cost was already spent). Export has neither risk. Treating it as a sixth generation type by default — the "reach for the familiar pattern" failure mode this document was asked to watch for — would import machinery (provider telemetry columns, a recovery path for "provider responded but we crashed before persisting," retry/attempt-number semantics) designed for a problem Export does not have. §8 makes this precise.

**What Export's actual risk shape is instead:** faithfulness (did the DOCX/HTML/Markdown genuinely say what the approved Content says, in the right order, with nothing silently dropped or reordered) and correctness of the gate (did it let through content that was never actually QA-approved, or block content that legitimately passed). Both are solvable deterministically — §2 and §6 are where the real engineering care in this phase belongs, not a provider-telemetry lifecycle.

## 1. Exact export source-of-truth (requirement 1)

An export request pins exactly four things, all read once at request time and never re-resolved mid-process or on a later view of the same export row:

| Pinned field | Source | Why exact, not "current" |
|---|---|---|
| `exports.brief_version_id` | The Brief version `blueprint_versions.brief_version_id` points to, for the Blueprint version being exported (BD1's existing lineage — Export does not independently choose a Brief version, it inherits the one the exported Blueprint version already pins). | Never re-read from `content_briefs.current_version_id` — matches the exact anti-pattern every prior phase's §0 already warned against (Blueprint's own original gap, Phase 4.4 §0). |
| `exports.blueprint_version_id` | `content_blueprints.current_version_id` **at the moment Export is requested**, captured once. | The Blueprint's leaf-node set (and therefore the exported document's structure) is fixed the instant the export starts — a concurrent Blueprint edit mid-export must not silently reshape the file being written. |
| `export_content_versions` (one row per leaf) | Each leaf node's `content_documents.current_version_id` **at the moment Export is requested**, captured once per leaf, in one batch read — not re-read per format, not re-read per file. | Same reasoning as Blueprint: a concurrent Content edit mid-export must not produce a file whose sections are drawn from different points in time from each other. |
| `exports.qa_report_id` (new, ED1) | The latest `qa_reports` row that satisfied the gate (§2) at request time. | Without this, an export has no durable record of *which* QA pass actually authorized it — a real, previously-unflagged gap, same class as Blueprint's missing `brief_version_id` and QA's missing `qa_findings.content_version_id`. An export must be able to answer "which QA report said this was OK to ship," permanently, even after later QA reports run. |

**"Never silently resolve a newer/current version" — the concrete failure mode this rule prevents:** without pinning, a `qa_report_id` that isn't stored anywhere would force every later "was this export actually authorized" question to re-run the staleness comparison against whatever is current *now* — which could by then say "yes, currently stale" even though it was legitimately clean at export time. The pin is the permanent, honest record of what was true when the button was clicked, exactly the same reasoning as every prior phase's lineage-pinning decision (BD1, CD3's `blueprint_node_id`, QD6's `qa_report_content_versions`).

**Reproducibility (requirement 7, restated precisely):** because all four pins are immutable FKs into already-immutable rows (Brief/Blueprint/Content versions never change in place — insert-only everywhere, CD5/BD5/QD5), re-reading a past `exports` row and re-running the exact same assembly+format logic against its four pinned ids reproduces byte-identical output at any future time, regardless of how many Brief/Blueprint/Content/QA changes have happened since. This is the direct payoff of the "insert-only, immutable snapshot" discipline this entire schema has enforced since Phase 4.3 — Export is the first stage to actually *need* full reproducibility as a first-class requirement, and the existing discipline already provides it for free.

## 2. Export gating (requirement 2)

**One deterministic function, `computeExportGate(project)`, four possible results — exactly what `phase-4-6-qa-ui-plan.md` §6 already specified, now given an owning implementation location.**

- **Allowed** — latest `qa_reports` exists, is not stale (§5 of the QA-UI plan's staleness test, reused unmodified), and `overall_status !== 'fail'`. PASS and WARN both allow export — only FAIL blocks, per the frozen wording: *"Export is blocked while any QA category is FAIL,"* not "while any category isn't PASS."
- **Blocked — FAIL** — latest QA is current and `overall_status === 'fail'`.
- **Blocked — stale** — latest QA exists but fails either staleness check (blueprint-version mismatch or any evaluated content-version no longer current, QD6). A stale report is treated identically to no report for gating purposes — a stale PASS must never be read as permission to export.
- **Blocked — no QA** — no `qa_reports` row exists.

**A real, previously-unflagged implementation gap this document is surfacing:** `page.tsx` currently computes `isStale`/`staleReason` **inline**, as local `const`s inside the page's render function (lines ~541–558), not as an exported, independently-callable function. QA UI reads it directly off the page's own computed props. **Required implementation-time refactor (not performed by this document): extract that logic into a pure function** — e.g. `lib/generation/qa/staleness.ts`'s `computeQaStaleness({ currentBlueprintVersionId, latestQaReport, qaReportContentVersions, currentContentVersionIds })` — taking already-fetched data as arguments (no new query, matching how it's computed today) and returning `{ isStale, staleReason }`. The Export tab's own gating then calls this same function with its own already-fetched data, plus the `overall_status !== 'fail'` check layered on top, producing `computeExportGate()`'s four-way result. **This is not optional polish — it is the literal meaning of requirement 2's "use ONE deterministic gating function."** Two independent re-implementations of the staleness comparison (one in `page.tsx` for QA, a second hand-rolled one for Export) would silently drift the moment either is edited without the other — exactly the "computed two different ways in two different places" failure this document was explicitly told to prevent.

**Where the gate is checked, precisely:** (1) client-side, to render the Export tab's current state (§9) — read-only, informational; (2) server-side, inside the export-triggering action itself, before any file is generated — the actual enforcement point, mirroring every prior phase's "server-side gate, not just UI-level" precedent (Blueprint's `brief_versions.status === 'approved'` check, Content's leaf+approved-Blueprint precondition check). A disabled button is not security (this project's own standing rule) — the export action must independently re-verify the gate against freshly-read data at request time, not trust whatever gate state the client happened to render.

## 3. Existing schema — is it sufficient? (requirement 3)

**Yes, with two small additive changes (ED3) — no new table.** Reviewed directly against `20260817000011_export.sql`:

- **`exports`** — `project_id`, `generation_run_id` (nullable, stays null — ED4), `brief_version_id`, `blueprint_version_id`, `formats` (jsonb), `status` (`export_status`), `requested_by`, `requested_at`, `completed_at`. **Missing:** `qa_report_id` (ED1) — the one real gap. Everything else needed for §1's pinning already exists.
- **`export_content_versions`** — `export_id`, `content_version_id`. Sufficient exactly as shipped: one row per leaf section pinned into this export, no changes needed. (No `blueprint_node_id` column needed on this table either, mirroring QD1's own reasoning for `qa_findings` — `content_versions.blueprint_node_id` is already reachable via the FK, no redundant column.)
- **`export_files`** — `export_id`, `format`, `file_name`, `storage_path`, `created_at`. **Missing:** `mime_type`, `size_bytes` (ED10) — needed for correct download response headers (§10) without a redundant Storage metadata round-trip at download time.
- **`export_status`** enum (`idle`|`running`|`done`|`failed`) — sufficient as-is; maps directly onto §8's lifecycle with no new value needed.
- **Existing foreign keys** — all correctly `on delete cascade` from `exports`/relevant parent, matching every other artifact table's cascade discipline; no change needed.

No new table is proposed, per the explicit instruction not to invent one unless required — the two column additions are narrow, justified individually (ED1, ED10), and both follow the exact "flag it, don't build it here" pattern already used for every prior phase's own schema gap.

## 4. RLS (requirement 4)

**All three tables have RLS enabled with zero policies** — confirmed directly from `20260817000013_enable_rls.sql` plus the takeover document's own policy-coverage table, the same "RLS enabled, zero policies" trap every prior phase has hit and closed (Brief, Blueprint, Content, QA). Required migration (not created here), reusing `can_access_project()`/`current_app_role()` only — no new `SECURITY DEFINER` helper, no new recursion risk (migrations 16/17's bug class):

**`exports`** (`project_id` exists directly on the table, same shape as `qa_reports`):
- SELECT: `can_access_project(project_id)`.
- INSERT: `can_access_project(project_id) and current_app_role() in ('team_lead', 'seo_manager')`.
- **UPDATE: `can_access_project(project_id) and current_app_role() in ('team_lead', 'seo_manager')`** — this is the one real difference from QA's "no UPDATE at all" stance (QD5), and it is deliberate, not an accidental weakening. §8's status lifecycle (`idle → running → done/failed`) requires updating the *same* `exports` row's `status`/`completed_at` as the export progresses — there is no head+version split for a single export attempt to insert-around the way Brief/Blueprint/Content do. This UPDATE is narrowly a status/timestamp transition on the row's own lifecycle fields, never a content mutation — the four pinned lineage columns (`brief_version_id`/`blueprint_version_id`/`qa_report_id`, ED1) are set once at INSERT and never touched by any UPDATE path this document proposes. **The immutable-snapshot guarantee (ED8) is about the *exported content*, not the status row's own bookkeeping fields** — an export's pinned inputs and generated files are exactly as immutable as every other artifact in this schema; only "is this export still in progress" is mutable, the same distinction Brief/Blueprint/Content/QA don't need because their generation state lives entirely in `generation_runs`, a table Export deliberately isn't using (ED4).

**`export_content_versions`** (join-through-parent via `exports.project_id`, same pattern as `blueprint_nodes`/`qa_report_content_versions`):
- SELECT/INSERT: `exists (select 1 from exports e where e.id = export_id and can_access_project(e.project_id) [and current_app_role() in (...) for INSERT])`.
- No UPDATE, no DELETE — these rows are written once, at export-creation time, and never revisited.

**`export_files`** (join-through-parent via `exports.project_id`, identical shape):
- SELECT/INSERT: same join-through-`exports` pattern.
- **No UPDATE.** A file row, once its format has been generated and its `storage_path` written, is never modified — this is where ED8's immutability guarantee is actually strict with no exception (unlike `exports` itself, which has the narrow status-lifecycle UPDATE above). If a format's generation fails, that's recorded on the parent `exports.status = 'failed'` (§8) — no per-file "failed" row is ever half-inserted; a file row's mere existence means its generation succeeded (§8's failure semantics).
- No DELETE anywhere, on any of the three tables — same as every other artifact table in this schema.

**Security is not weakened anywhere in this design** — Content Writer remains read-only on Export exactly as on every other artifact table; only `team_lead`/`seo_manager` can trigger, progress, or write an export.

## 5. Export formats (requirement 5)

**Canonical input to every format, without exception: the one assembled representation from §6** — an ordered array of nodes, each `{ level, title, isLeaf, body: string | null }` (Markdown body for leaf nodes, `null` for structural nodes, matching CD6's existing "structural node contributes a heading only" rule exactly), plus a small `metadata` object (`{ title, h1, market, contentType, exportedAt, projectName }` sourced from the pinned Brief version + `projects` row). No format reads from the database a second time — every format-specific function receives this in-memory object and this object alone.

### Markdown

- **Transform:** near-identity. Each node becomes `#`-repeated-by-level heading (capped at `######`, H1 for level 0/1 per the existing root-node convention) followed by its body verbatim (already stored as plain Markdown, CD5/CD6 — no re-encoding needed).
- **Headings:** direct level→`#`-count mapping, matching the Blueprint tree's own `level` field, the same convention already rendered in the Content Editor and QA `intent` assembly.
- **Lists/links/quotes:** passthrough, unchanged — the stored body is already canonical Markdown; this format performs zero content transformation, only heading-prefix insertion and section concatenation.
- **Metadata:** a small YAML-ish frontmatter block or a plain leading `# Title` + byline line (implementation-time choice, not decided here) — kept minimal, not a second document-structure system.
- **Filename:** `{project-slug}-{exportedAt-date}.md` (slugified project name — reuses whatever slugification, if any, already exists elsewhere in the codebase; if none exists, a simple lowercase/hyphenate/strip-non-alphanumeric function, not a new dependency).
- **Encoding:** UTF-8, no BOM (matches every other text asset already stored in this system).

### HTML

- **Transform:** extends `lib/format/markdown.tsx`'s existing block/inline parser (H2/H3, bold, italic, lists, links, paragraphs) unmodified for the inline/block logic, wrapped in a minimal document shell (`<!doctype html><html><head><meta charset="utf-8"><title>…</title></head><body>…</body></html>`) with the node-level heading tags generated directly from `level` (same mapping as Markdown, `<h1>`–`<h6>`) rather than re-parsing `#`-prefixed Markdown headings through the existing parser (the existing parser's job is inline content within a section body, not top-level document structure — cleanly separated, no duplicate heading-detection logic).
- **Formatting rules:** identical safety discipline already proven in `lib/format/markdown.tsx` — every piece of source text becomes text content, never `dangerouslySetInnerHTML`'d as HTML from the stored Markdown; the one real HTML attribute derived from content (a link's `href`) is whitelisted against the same safe-scheme pattern (`http(s):`, `mailto:`, `/`, `#`) already implemented there. This is a **server-side string-building port** of the same parser's logic (React JSX → HTML string), not a new parser and not a new trust model.
- **Headings/lists/links/quotes:** same mapping as the Content Editor's existing renderer — `##`/`###` → `<h2>`/`<h3>` (extended to `<h1>`–`<h6>` for the export's own document-level headings, §above), `*`/`_` → `<em>`, `**`/`__` → `<strong>`, `-`/`1.` lists → `<ul>`/`<ol>`, `[text](url)` → `<a href="…">` (safe-scheme-filtered).
- **Metadata:** real `<head>` tags (`<title>`, `<meta name="description">` sourced from the Brief's own synthesis if a suitable field exists, `<meta charset="utf-8">`) — not decorative, actually useful if the exported HTML is ever opened directly in a browser or handed to a CMS importer.
- **Filename:** `{project-slug}-{exportedAt-date}.html`.
- **Encoding:** UTF-8, declared via `<meta charset="utf-8">`.

### Structured JSON

- **Transform:** none — a direct, typed serialization of the assembled representation itself (§6), plus the four pinned lineage ids (§1) and per-section metadata (`blueprintNodeId`, `contentVersionId`, `evidenceUsed` if useful for a downstream consumer to see provenance). This is the "free" format in the sense that it requires no rendering logic at all, only a `JSON.stringify` of an already-typed object — the assembled representation *is* the Structured JSON output, modulo field naming.
- **Formatting rules:** none needed — JSON has no ambiguous heading/list/link representation to design; each node is `{ level, title, isLeaf, body, blueprintNodeId, contentVersionId }` verbatim.
- **Headings/lists/links/quotes:** not applicable — these remain embedded as raw Markdown syntax inside each node's `body` string (this format does not attempt to parse Markdown into a structured AST for lists/links; that would be new parsing logic with no demonstrated consumer need, the same "don't build ahead of a demonstrated need" discipline as ED10's rejected checksum).
- **Metadata:** the full pinned-lineage block (§1) as first-class JSON fields — this is the one format where the export's own provenance is genuinely useful to a machine reader, not just a human one.
- **Filename:** `{project-slug}-{exportedAt-date}.json`.
- **Encoding:** UTF-8, standard JSON (no BOM).

### DOCX

- **Transform:** the one format requiring an actual new dependency — no DOCX-writing capability exists anywhere in this codebase today (confirmed by searching `package.json`; no `docx`, `mammoth`, or equivalent library present). **Recommended, not installed by this document:** a minimal, focused DOCX-generation library (e.g. the `docx` npm package — pure JS, OOXML-writing, no native binary, no headless-browser dependency) used server-side only, inside the export action — never shipped to the client bundle, so it does not touch the "avoid heavyweight UI dependencies" Toyota principle (§11), which concerns client-side bundle weight, not server-only Node dependencies. This is a deliberate, narrow, justified exception — flagged explicitly as a new dependency requiring the user's own install/approval at implementation time, not silently assumed.
- **Formatting rules:** headings map to the library's native heading-style levels (`Heading1`–`Heading6`, matching `level` directly — Word's own semantic heading styles, not manually-sized bold text, so the resulting document has a real, navigable outline in Word/Google Docs). Bold/italic map to native run-formatting properties. Lists map to the library's native numbered/bulleted list paragraph styles (not manually-typed `1.`/`-` characters, which would defeat Word's own list renumbering/formatting).
- **Lists:** same bullet/numbered distinction as HTML, using the library's native list-paragraph API — a loose-vs-tight list distinction is not preserved (DOCX's native list model does not have a clean equivalent for this Markdown nuance; a reasonable implementation-time simplification, not designed further here).
- **Links:** native OOXML hyperlink runs (blue, underlined, actually clickable in Word), same safe-scheme whitelist as HTML — a link whose target fails the whitelist renders as plain non-clickable text, same rule as HTML/Markdown display.
- **Quotes:** Markdown does not appear anywhere in this schema's stored content to use blockquote syntax explicitly (`content_versions.body` has no observed `>`-prefixed convention in the Content prompt's own instructions) — if a body ever contains one, render it as an indented paragraph with the library's built-in "Quote" style if available, otherwise a plain indented paragraph; not a load-bearing requirement, since no upstream stage currently produces blockquote Markdown.
- **Metadata:** OOXML core-properties (`Title`, `Creator` = project's organization name or a fixed app name, `Created` = `exportedAt`) — supported natively by most DOCX libraries as a metadata object, not hand-written XML.
- **Filename:** `{project-slug}-{exportedAt-date}.docx`.
- **Encoding:** binary (OOXML zip container) — `mime_type` (ED10) is what makes this format's download correctly typed, since the file itself has no meaningful "character encoding" the way the three text formats do.

## 6. Content assembly (requirement 6)

**One function, called exactly once per export request, producing the in-memory representation every format (§5) reads from:**

```
assembleExportDocument({ blueprintVersionId, leafContentVersions }): AssembledNode[]
```

- Fetch the full `blueprint_nodes` set for the pinned `blueprintVersionId` (one query — the exact same shape `page.tsx`/Content Editor/QA's `lineage.ts` already fetch for their own purposes, reused, not duplicated logic).
- Order via `orderNodesByDocumentPosition()` (`lib/generation/blueprint/tree-order.ts`, unmodified) — **the same canonical DFS helper already proven correct for a mixed-depth tree**, explicitly not a raw `(level, position)` flat sort (the exact bug this helper's own doc comment warns against) and explicitly never relying on whichever order Postgres happens to return rows in (database row order is an implementation detail, never a document-order guarantee — this is the literal meaning of requirement 6's "must never use database row order accidentally").
- For each ordered node: if leaf, look up its pinned `content_versions.id` (from `export_content_versions`, §1 — **not** `content_documents.current_version_id` re-read fresh, which could differ from what was pinned if a concurrent edit landed between gate-check and assembly) and attach its `body`; if structural, attach `body: null`.
- Return the flat, ordered array — `AssembledNode[]` — as the one shared representation every format function in §5 consumes.

**Never using database row order accidentally, made concrete:** the query fetching `blueprint_nodes` has no meaningful `ORDER BY` guarantee on its own (Postgres does not promise row order without an explicit `ORDER BY`, and even an `ORDER BY id`/`ORDER BY created_at` would not reconstruct document order for a tree) — `orderNodesByDocumentPosition()` is applied to the fetched array in application code, in memory, exactly once, immediately after fetch and before anything reads it — the same discipline already correctly followed by Content Editor's sidebar and QA's `intent` assembly, both of which had to be fixed onto this helper after an earlier flat-sort bug (`tree-order.ts`'s own doc comment records this history).

## 7. Version snapshot (requirement 7)

Directly restates and closes §1 and ED8: an `exports` row, once created, permanently records `brief_version_id`, `blueprint_version_id`, the full `export_content_versions` leaf set, and `qa_report_id` (ED1) — four immutable FKs into rows that are themselves already immutable by construction (every version table in this schema is insert-only, CD5/BD5/QD5). **Reproducibility is therefore a property of the schema design, not something Export needs to build separately** — re-running §6's assembly function against a past export's four pinned ids at any future date reconstructs the identical `AssembledNode[]` array (same nodes, same bodies, same order — `orderNodesByDocumentPosition()` is itself pure and deterministic), and re-running any §5 format function against that identical array produces byte-identical output. The only thing that could change output reproducibility is a bug in the format functions themselves changing behavior over time (a code change, not a data change) — an ordinary versioning-of-code concern, not something this document's data-architecture needs to additionally guard against.

## 8. Status lifecycle (requirement 8)

**`idle → running → done` / `failed`, tracked directly on the `exports` row's own `status` column** — matching the existing `export_status` enum exactly, no new value needed.

- **`idle`**: the transient pre-insert state — in practice, an `exports` row is only ever inserted already at `running` (the INSERT and the "user clicked Export" action are the same moment; there is no meaningful "idle row sitting in the database" state to represent — `idle` exists in the enum as the sensible default/placeholder value, matching how other status enums in this schema define a default that's rarely, if ever, actually queried against).
- **`running`**: set at INSERT time, immediately after the gate check (§2) passes server-side. The row's four pinned lineage fields (§1) are written at this same INSERT — this is the one and only INSERT for this export attempt.
- **`done`**: set once every requested format (ED7) has successfully generated its file and its `export_files` row is written. `completed_at` set to the same timestamp.
- **`failed`**: set if any requested format's generation throws. **No partial success state is introduced** — if 3 of 4 requested formats succeeded and the 4th threw, the whole export is `failed`, and none of the 3 successful `export_files` rows are left dangling as if the export completed (implementation detail: either don't write any `export_files` row until all requested formats have generated successfully in memory, then insert them all together — mirroring the "insert everything together before the flip" discipline already used by QA's `artifact_persisted` step, §10 of the QA plan — or, if a partial-success UX is later found genuinely valuable, that's an explicit future decision, not assumed here). This document recommends the **all-or-nothing** shape as the V1 default, matching Design V1's own binary success/failure framing for Export (`docs/design/README.md`'s Export tab spec has no partial-success state).

**Why not the Generation Engine (ED4, restated with the concrete reasoning):**

1. **No provider call exists to make D1's "durably store raw output before parsing" guarantee meaningful.** D1 exists because a real dollar cost is spent calling Anthropic before the app has any control over whether persistence succeeds — losing that response would mean re-paying for an identical call. Export's "raw output" (the assembled document) and "the persisted artifact" (the generated file) are produced by the same deterministic, free, in-process computation — there is no expensive, non-reproducible step whose result needs protecting from a crash between "received" and "persisted." Re-running `assembleExportDocument()` after a crash costs nothing (a handful of already-fast indexed queries), unlike re-calling Claude.
2. **`recordProviderCompleted`/`recordArtifactPersisted`'s two-phase split exists to distinguish "the model responded" from "we finished writing it down"** — a distinction with no analog here, since there's no separate "provider responded" moment at all.
3. **The partial unique index (D2) exists to prevent duplicate-click/simultaneous-user races on an expensive, slow, external call.** File generation is fast, cheap, and idempotent-in-effect (ED11) — two concurrent export clicks simply produce two valid, independently-retrievable snapshots (ED8), which is correct behavior, not a race to guard against. No `generation_runs`-style uniqueness index is needed on `exports`.
4. **Telemetry (D7) exists to track AI provider cost/tokens** — Export has zero tokens, zero provider cost, nothing D7's columns are designed to capture. Using `generation_runs` here would mean either leaving 15 of D7's columns permanently null (a schema smell — a table whose columns mostly don't apply to one of its own `type` values) or inventing Export-specific telemetry that has no real content to report.

**The one narrow exception, stated for completeness, not proposed as a requirement:** if a future revision of this phase decides Export needs its own audit trail comparable to `generation_events`' timeline (a human-readable "who exported what when" log beyond the `exports` row's own `requested_by`/`requested_at`/`completed_at` columns, which already answer that), the existing `exports.generation_run_id` column could theoretically be populated with a `generation_runs` row of `type = 'export'` (the enum value already exists, confirmed unused since Phase 0) purely as an audit-log entry, never as a provider-telemetry record — but this is speculative, not needed by anything designed in this document, and should not be built now (mirrors the same "flag it, don't build it" discipline used throughout this document's own gap-flagging). **Recommendation: leave `generation_run_id` null for every real export** — `exports`' own `requested_by`/`requested_at`/`completed_at` columns already fully answer "who exported what when," making a second audit mechanism redundant.

## 9. Export UI (requirement 9)

Design V1's frozen prototype (`docs/design/README.md` line 95) already specifies the shape: *"format checkboxes (Markdown/HTML/DOCX/Structured JSON) → validation banner (blocked if QA has a failure) → Export → exporting spinner → complete (file list with download links)."* This section makes that concrete against the real schema (§1–§8) and the real gating function (§2):

- **Unlock condition:** matches Content Editor/QA's own threshold — `projects.status` reaching `blueprint_approved` or later (the same `contentEditorUnlocked` boolean `project-tabs.tsx` already threads through, per its own doc comment: *"Export stays hardcoded locked, unchanged; this component does not touch its lock state (Phase 4.7's job)"* — this phase is exactly the one that changes that line). Unlocking the *tab* is a separate, looser condition from being *allowed to export* (§2's gate) — a user should be able to open the Export tab to see *why* they're blocked (no QA yet, FAIL, stale) without Export itself being reachable, same "locked tab vs. gated action" distinction already drawn for the Brief/Blueprint/Content tabs' own approval gates.
- **Current gating state (§2's four-way result), rendered exactly like the QA tab's own banner discipline** (`qa-review.tsx`'s existing PASS/WARN/FAIL/stale banner pattern, reused visually, not reinvented): Allowed → "Ready to export" with the format checkboxes enabled; Blocked-FAIL → "N finding(s) must be resolved before export" with a direct link back to the QA tab's category cards (not duplicating finding detail here, matching the QA-UI plan's own §6 instruction); Blocked-stale → "QA is out of date — re-run before exporting," styled with the same urgency as QA tab's own stale-report treatment (§7 of the QA-UI plan: "the loudest thing on the page, overriding even a stale PASS's would-be reassuring green"); Blocked-no-QA → "Run QA before exporting" with a link to the QA tab.
- **Selected format(s):** checkboxes, matching Design V1's own UI exactly — no radio-button single-select, multiple formats may be requested in one export (ED7).
- **Export action:** disabled unless gate is Allowed and at least one format is checked — same "disabled button is not security, server re-checks independently" discipline as §2's own closing paragraph; the disabled state is a UX courtesy, not the enforcement point.
- **Progress/state:** `running` → a spinner/progress state per Design V1's own "exporting spinner" language — given §8's typical sub-second-to-low-seconds generation time (no AI call, no network round-trip beyond Storage writes), this is likely to be visually brief for most documents; still worth an explicit loading state rather than an instant flash, for documents with many sections and/or the DOCX format's heavier synchronous work.
- **Success/download state:** `done` → Design V1's "complete (file list with download links)" — one row per requested format, each linking to that format's `export_files.storage_path` via a signed URL (§10) generated at render time, not stored — never a permanently-public link, matching the existing private-`project-files`-bucket convention every other stage already uses.
- **Failure state:** `failed` → a plain error banner with a retry action that triggers a **new** export request (ED8 — never a "retry the same row" action, since a failed row has no valid partial state to resume from, §8's all-or-nothing design).
- **Previous exports/history:** **supported by the existing schema, cheap to add, recommended for V1** — `exports` is already queryable `ORDER BY requested_at DESC` per project (mirrors how QA reports are already listed by recency, §10 of the QA plan: *"latest for this project" is a plain `ORDER BY run_at DESC LIMIT 1` query* — history here is the same query without the `LIMIT 1`). A simple list of past exports (`requested_at`, `requested_by`, formats, status, and — for `done` rows — the same download links) costs one additional query beyond what rendering the current gate state already requires, and directly demonstrates ED8's reproducibility guarantee to the user (a past export remains downloadable and correct even after the project has moved on). Recommended as in-scope for the Export tab's first build, not deferred — Design V1's own frozen prototype doesn't explicitly show a history list, but nothing in it forecloses one either, and the schema already supports it for free.

## 10. Download/file handling (requirement 10)

**`export_files` stores `storage_path`, `mime_type`, `size_bytes` (ED10, ED3) — no `checksum`.**

- **`storage_path`** (existing column) — same `project-files` private-bucket convention as every other stage's `output_ref`, e.g. `{projectId}/exports/{exportId}/{format}.{ext}`.
- **`mime_type`** (new) — set once at write time from the format (`text/markdown`, `text/html`, `application/json`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document` for DOCX) — stored rather than re-derived at download time so the download response's `Content-Type` header is correct without an extra Storage metadata lookup (a real, small Toyota-principle win: one fewer round-trip per download, §11).
- **`size_bytes`** (new) — set once at write time from the generated buffer's own length — useful for the history list (§9) to show file size without a Storage `HEAD` request, and for basic sanity-checking (a `0`-byte file is an obvious signal something went wrong, worth surfacing even without a full checksum).
- **`checksum`** — explicitly rejected (ED10's full reasoning above) — no demonstrated corruption risk anywhere in this pipeline's existing Storage usage to justify the added column and the (equally speculative) verification logic that would need to consume it.

**Avoiding duplicate file generation:** already fully addressed by ED5 (assemble once) and ED11 (no dedup layer needed, by construction) — restated here only to confirm requirement 10's explicit ask is satisfied: within one export request, each requested format is generated exactly once, from the one shared assembled representation, and written to Storage exactly once per format.

## 11. Toyota Performance Principle — applied concretely to Export

- **No AI calls** — zero, by design (ED4, §0). The only calls in this entire phase are: a handful of already-fast, already-indexed Postgres SELECTs (Blueprint tree, pinned content versions, the QA report for gating) and Storage writes for the generated files.
- **No unnecessary DB queries** — the gate check (§2) and the assembly step (§6) both reuse data shapes already fetched elsewhere in this pipeline (the same Blueprint-tree and content-version queries Content Editor/QA already perform) — no new query pattern is introduced, only a new consumer of existing patterns. The QA-report lookup for `qa_report_id` (§1) reuses the exact same "latest report" query QA's own tab already performs.
- **Assemble once, format from the same in-memory representation** — ED5's central rule; this is the single biggest lever in this entire design for keeping Export fast and avoiding accidental N-times-slower behavior as more formats are requested in one export.
- **No duplicate traversal of the content tree per format** — direct consequence of ED5: `assembleExportDocument()` runs once regardless of whether 1 or 4 formats are requested; each format function is a pure `AssembledNode[] → string | Buffer` transform with no independent tree-walking of its own.
- **Generate only the requested format** — ED7's explicit rule; a project that only ever wants Markdown never pays for DOCX generation (the one format with real per-call cost, given the OOXML library's synchronous document-building work).
- **Keep export deterministic and fast** — no provider round-trip (the dominant latency cost in every prior stage) means Export's own latency floor is Storage-write speed and, for DOCX, in-process document-building time — both small and bounded relative to a typical Anthropic call's multi-second latency.
- **Avoid heavyweight UI dependencies** — the one new dependency this phase introduces (a DOCX-writing library, §5) is server-only, never bundled to the client — the Export tab's own client component needs no new dependency beyond what Design V1's existing checkbox/button/banner primitives (`Card`, `StatusBadge`, reused unmodified per every prior phase's own "zero new components" discipline) already provide.
- **Avoid creating duplicate sources of truth** — ED2's gating-function extraction directly serves this: one `computeQaStaleness()` function, called by both QA tab and Export tab, is the explicit fix for a duplicate-logic risk this document is not willing to let land as two copies.
- **Track latency on major operations** — not proposed as a new telemetry system (that would contradict D6/D7's "capture only, no dashboard" scope and this document's own ED4 reasoning that Export doesn't need `generation_runs`-style telemetry) — if operational visibility into Export latency is ever needed, ordinary application logging/APM (Sentry, already integrated per the takeover doc's own architecture summary) is the correct mechanism, not a new DB column.

## Export bypass — "Export without QA" (ED12, locked 2026-08-20, LEAVES-02)

**Status: locked architecture. Not implemented — no migration, no code, no Anthropic calls made producing or locking this section**, matching this document's own planning-only constraint. Originally raised and analyzed as a proposal during LEAVES-01 (real production use surfaced a legitimate need ED2's gate does not accommodate: an expert, `team_lead`/`seo_manager`, sometimes needs to export despite No QA / stale QA / QA FAIL — e.g. a time-sensitive publish where the team has already manually reviewed the flagged sections and judges the residual risk acceptable); reviewed and **locked as ED12** in this pass (LEAVES-02), without amendment to the original analysis. ED2's gate stays exactly as strict as designed for the *normal* path — this is a distinct, explicit override sitting outside that gate, never a loosening of it, and never a second gating algorithm (requirement 10, restated): `computeExportGate()` remains the one deterministic function; bypass is a user action layered on top of its result, not an alternate way of computing that result.

**Proposed behavior:**

- The normal gate (§2, ED2) is completely unchanged: Allowed only on non-stale QA with `overall_status !== 'fail'`. The normal "Export" action still only fires when Allowed.
- When the gate is **Blocked** (any of its three reasons — FAIL, stale, no-QA), the Export tab additionally offers a separate, visually distinct **"Export without QA"** action.
- Clicking it opens an **explicit confirmation** step (a real dialog/step requiring a second deliberate action, not a single click double-purposed) that states plainly what is being bypassed (e.g. "This project has FAIL findings" / "QA has not been run" / "QA is out of date") before proceeding — matching the task's own "no hidden bypass, no automatic bypass" requirement.
- On confirmation, the export proceeds through the exact same pipeline as a normal export (§6 assembly, §5 formats, §8 lifecycle) — bypass changes only *whether the gate blocked it*, never *how* the file is built.

**Schema analysis — can the existing (+ED1) schema support this cleanly?**

**Mostly, with one small additive field.** `exports.qa_report_id` (ED1, this document's own proposed addition) already does most of the required work correctly, with no change needed to its own meaning: it should be populated with whatever the *latest* `qa_reports` row is at export time, **even when that report is FAIL or stale** — recording *which* report was overridden, not just that one was. It stays `null` only in the genuine "no QA report exists at all" case (the task's own explicit requirement: "preserve `qa_report_id = null` when none exists"). This is exactly ED1's existing behavior already, unmodified — no change needed here.

**What the existing schema (+ED1) cannot express on its own: *whether* an export was a normal Allowed export or an explicit bypass.** `qa_report_id` being non-null is ambiguous between "this was a normal export and QA happened to PASS" and "this was a bypassed export of a FAIL/stale report" — both leave `qa_report_id` pointing at a real row. Distinguishing them is exactly the task's own "preserve whether the export bypassed QA" and "must never masquerade as a normal approved/QA-passed export" requirements, and cannot be inferred after the fact from `qa_report_id` alone (a later observer would have to re-run the same staleness/FAIL comparison against historical data to guess — fragile, and exactly the kind of "recomputed, not recorded" gap this schema's own lineage-pinning discipline exists to avoid, see §1/ED1's own reasoning).

**Locked, small, additive schema field (ED12; not created by this document — a migration is still implementation's job, not this planning pass's): `exports.qa_bypassed boolean not null default false`.** Set `true` only on the explicit bypass path; every normal, gate-Allowed export stays `false`. This is deliberately a boolean, not a third `export_status` value or a repurposing of an existing column — `status` already means lifecycle progress (`idle → running → done/failed`, §8, unchanged meaning); conflating "was this authorized normally or bypassed" into that same column would blur two orthogonal concepts the way this document has otherwise been careful to keep separate (ED4's own reasoning for keeping Export off the Generation Engine follows the identical discipline: don't reuse a column/table for a concept it wasn't designed to carry). No other new column is proposed — `requested_by`/`requested_at` (existing) already answer "who confirmed the bypass and when," satisfying the "require explicit user confirmation" requirement's own audit trail without a dedicated confirmation-text column.

**Server-side enforcement (restated, not weakened):** the export action must independently verify, matching §2's own "disabled button is not security" rule: if the request claims `bypass: false`, the gate must actually be Allowed server-side or the request is rejected; if `bypass: true`, the gate must actually be Blocked (any reason) server-side or the request is rejected — a bypass flag is never accepted when nothing is actually being bypassed, which would otherwise let a normal export silently and pointlessly mark itself unverified, or worse, let a client fabricate `bypass: false` against a server that should have blocked it.

**How this stays visually and permanently distinguishable (never masquerading as approved) — requirement 8, locked:**

- **In the Export tab's history/download list (§9):** a bypassed export renders with a distinct, unmistakable label — e.g. an "Unverified" badge in the same danger/warning tone family QA's own FAIL badge uses (`StatusBadge`, reused, not a new visual language) — never the same neutral/success treatment a normal completed export gets. This is read directly off `exports.qa_bypassed`, never inferred from `qa_report_id`'s mere presence (ED12's own reasoning for why that column alone was insufficient).
- **Structured JSON** (§5): already carries the full pinned-lineage block as first-class fields (§1/§7's "the one format where the export's own provenance is genuinely useful to a machine reader"). Locked addition: two more first-class fields in that same block — `qaBypassed: boolean` (mirrors `exports.qa_bypassed` exactly) and `qaState: { reportId: string | null, overallStatus: "pass" | "warn" | "fail" | null, wasStale: boolean | null }` (`null` fields when no report existed at export time) — a machine reader can determine the export's verification state without a second query against `exports`/`qa_reports`.
- **Markdown/HTML/DOCX** (§5): a single, un-removable **export-metadata line**, placed in the exact same document-metadata location each format already reserves for `title`/`exportedAt` (§5's per-format "Metadata" row — Markdown's frontmatter/byline line, HTML's `<meta>`/head block, DOCX's OOXML core-properties `Subject` or an equivalent lightweight properties field) — never inserted into the article body itself, so no publishable content is altered. Exact wording, locked: **"Export status: Unverified — exported without a passing QA review"** for a bypassed export with no report or a FAIL/stale one; a normal export's existing metadata is unchanged (no new line added when `qa_bypassed = false`, avoiding the opposite failure mode of implying every export needs a disclaimer). This is deliberately a metadata-only convention, not a body-content change — Markdown's own canonical storage/rendering (`content_versions.body`, CD5/CD6, Phase 4.5) and every format's transform rules (§5) stay exactly as this document already specifies; the bypass notice rides in the same place `exportedAt`/`title` already ride, not a new content block.
- **No numeric score anywhere** — the bypass banner/label/metadata line states the plain fact ("exported without a passing QA review"), never a computed risk number or percentage, matching this document's own §11/ED-table discipline against inventing scores QA itself never had (QD8/Design V1 rule #6, reaffirmed).

**Server-side enforcement (requirement 6, restated as locked, not weakened):** matching §2's own "disabled button is not security" rule — if the request claims `bypass: false`, the gate must actually be Allowed server-side or the request is rejected; if `bypass: true`, the gate must actually be Blocked (any reason) server-side or the request is rejected. A bypass flag is never accepted when nothing is actually being bypassed (which would let a normal export pointlessly mark itself unverified), and a normal-export request is never allowed to silently succeed against a server-side-Blocked gate just because the client rendered it as available. The client can only *request* a bypass; it can never *force* one, and it can never disguise one as normal.

**Relationship to ED1–ED11:** unchanged, per requirement 9 — ED12 adds one new column (`exports.qa_bypassed`) and layers an explicit user action on top of ED2's existing `computeExportGate()`; it does not modify ED1 (`qa_report_id`'s own meaning is unchanged and reused as-is), ED3–ED11, or any other locked decision in this document.

## Export provenance tiers (ED13, locked 2026-08-20, LEAVES-04)

**Status: locked architecture. Not implemented — no migration, no code, no Anthropic calls made producing or locking this section**, matching this document's own planning-only constraint. Companion to `docs/architecture/phase-4-6-qa-plan.md`'s QD9 (Partial QA — user-selected category subset), raised as a proposal during LEAVES-03 and **locked, without amendment, as ED13** during LEAVES-04, alongside QD9 itself. ED12 already distinguishes normal-verified export from a fully-bypassed one; QD9 introduces a real third state — a report that genuinely ran and genuinely passed, just over fewer than all 9 categories — that ED12's binary `qa_bypassed` cannot represent on its own. ED13 extends `computeExportGate()`'s *output*, not its *mechanism* (requirement 10, unchanged): still one deterministic function, no second gating algorithm.

**Provenance — three tiers, computed, not stored redundantly (requirement C).**

| Tier | Condition | `qa_bypassed` |
|---|---|---|
| **Verified** | Latest QA report is current (non-stale), `overall_status !== 'fail'`, and `skipped_categories` is empty (a full 9-category run). | `false` |
| **Partially verified** | Latest QA report is current, `overall_status !== 'fail'`, and `skipped_categories` is non-empty (QD9). | `false` |
| **Unverified** | The export was created via the ED12 bypass path — regardless of whether a report existed, and regardless of whether that report (if any) was full or partial. | `true` |

**Deliberately not a new stored column.** `exports.qa_report_id` (ED1) and `exports.qa_bypassed` (ED12) already fully determine the tier at any future time, because both the export row and the joined `qa_reports` row (including QD9's proposed `evaluated_categories`/`skipped_categories`) are immutable once written (ED8, QD5) — unlike staleness, which depends on *external*, still-changing state, "was this report full or partial" is an *intrinsic*, permanently fixed property of an already-immutable report row. Storing it a second time on `exports` would be exactly the duplicate-source-of-truth this document's own §11/Toyota discipline argues against elsewhere. The tier is computed once at export time (to decide gating and to bake a frozen copy into the generated files' own metadata, below) and is safely re-computable identically at any later time for the history list/UI (§9).

**B. Export behavior per state (requirement B) — extending, not replacing, ED2's four-way gate:**

| QA state | Gate outcome | Tier if exported | Path |
|---|---|---|---|
| **Full QA, current, not FAIL** | Allowed | Verified | Normal Export button, no extra confirmation (ED2, unchanged). |
| **Partial QA, current, not FAIL among evaluated categories** | Allowed | Partially verified | Normal Export button — **no confirmation step** (ED14, locked 2026-08-20, corrects this row's original draft language below), only an informational "N of 9 categories evaluated" banner naming what was skipped, per requirement H's "never silently" — informed, not gated. |
| **No QA report exists** | Blocked — no-QA | Unverified | ED12 bypass only. |
| **Stale QA (full or partial)** | Blocked — stale | Unverified | ED12 bypass only. QD9 does not add a "partial-and-stale" special case — staleness blocks identically regardless of category coverage (QD6, untouched). |
| **Failed QA (full or partial — any FAIL among evaluated categories)** | Blocked — FAIL | Unverified | ED12 bypass only. A FAIL is a FAIL regardless of how many categories were checked (QD9's own §G table: partial QA does not soften ED12's bar) — a partial report cannot be "partially exported" around its own FAIL. |

The **only** two paths that produce a real, gate-Allowed, non-bypass export are full-Verified and partial-Partially-verified — every Blocked state (no-QA, stale, or FAIL, regardless of full/partial) funnels through the exact same ED12 bypass action, unchanged. This keeps ED12 doing exactly one job (the human override of an otherwise-blocking gate) while QD9/ED13 handles an entirely different job (labeling a *non-blocking*, real result honestly by its actual scope).

**Why partial QA needs no confirmation at all, unlike ED12 (corrected 2026-08-20, ED14/EXPORT-04 — this paragraph originally argued for a lightweight confirmation step; that conclusion is superseded, kept here struck through in spirit for the historical record rather than deleted):** ED12's confirmation exists because the gate *would have blocked* and a human is overriding that judgment — a materially higher-stakes action with nothing forcing the human to even notice the risk otherwise. A Partially-verified export's gate is genuinely **Allowed** — the categories that were checked, passed — and the "N of 9 evaluated" banner (§6 of the Export Tab UI section) already surfaces the incomplete-coverage fact inline, in the same place the Export button lives, before the click, satisfying requirement H's "never silently" without needing a second, separate confirming action. Adding a confirmation step on top of an already-visible banner would be friction with no corresponding safety gain — the informing already happened; gating on top of it would only be theater. ED12 and Partial QA remain two different flows (requirement 7 of LEAVES-04, unchanged) — they simply differ in *how* they inform, not in *whether* one needs a click-through and the other doesn't.

**C. Metadata representation per format (requirement 8's own instruction, extended for the partial tier) — no publishable content altered, same discipline as ED12's own metadata rule:**

- **Structured JSON:** the `qaState` object (ED12) gains its natural extension: `{ reportId, overallStatus, wasStale, evaluatedCategories: string[], skippedCategories: string[] }` — a machine reader can already tell full-vs-partial from array length without a new boolean, so no separate `isPartial` field is proposed (avoiding the exact redundant-flag pattern this document just argued against for the DB schema, applied consistently to the file format too). `qaBypassed` (ED12) is included unchanged.
- **Markdown/HTML/DOCX:** the same single metadata line ED12 already reserves gets a third wording variant, still one line, still in the same document-metadata location, still never inserted into the article body: **"Export status: Partially verified — N of 9 QA categories evaluated (skipped: …)"** for the Partially-verified tier, alongside ED12's existing "Unverified" wording and the (unchanged, silent-by-default) Verified tier, which still adds no line at all — consistent with ED12's own "no line added when nothing needs disclosing" rule.

**D. Cost/performance (requirement F) — Export's own share of the saving.** Export itself does no QA computation (ED4, unchanged) — the cost saving lives entirely upstream, in QD9's own reduced/zero LLM calls at QA-run time (`phase-4-6-qa-plan.md` §F). ED13 adds no new query beyond what ED1's existing `qa_report_id` join already requires — reading `evaluated_categories`/`skipped_categories` off the same already-joined `qa_reports` row costs nothing extra.

**E. Relationship to ED1–ED12 — unchanged, per requirement 9's spirit applied to this new proposal too.** ED13 does not modify ED1 (`qa_report_id`'s meaning is exactly as locked), ED2 (`computeExportGate()` gains a richer *output*, not a new *algorithm* — still the one function, requirement 10), ED4 (Export still performs zero QA computation itself), or ED12 (the bypass path, its confirmation flow, its `qa_bypassed` column, and its "never means QA passed" rule are all completely unchanged — ED13 only adds two *new* tiers alongside the Unverified tier ED12 already defined, it does not touch how Unverified itself works).

## Export Tab UI (ED14, locked 2026-08-20, EXPORT-04)

**Status: locked UI architecture. Not implemented — no code, no formatters, no Anthropic calls, no migration made producing or locking this section**, matching this document's own planning-only constraint. Builds directly on the already-implemented data-fetching layer (`page.tsx`'s `exportData`, EXPORT-03) and the already-locked gate/tier logic (ED2/ED12/ED13) — this section designs only the tab's presentation and interaction, reusing every value `exportData` already computes, never recomputing gate or staleness client-side (Toyota, §10 below). Supersedes §9's earlier, looser sketch of the same surface where the two disagree — §9 is left unedited as the historical record of the original planning pass; this section is authoritative.

### 1. Export tab access (requirement 1)

**No new state machine.** The Export tab reuses `contentEditorUnlocked` exactly — the same boolean `project-tabs.tsx` already threads through for Content Editor and QA (itself derived from `projects.status` reaching `blueprint_approved` or later, unchanged). This is the same "real project-state derivation already used by the Generation Pipeline" the task asks for, not a fourth bespoke condition.

**Two distinct layers, not one, restated precisely now that `exportData` exists:** (1) the *tab* is reachable once `contentEditorUnlocked` is true — a user can always open Export to see *why* they're blocked; (2) the *action* is gated separately by `exportData.snapshotEligibility` and `exportData.gate`, both already computed server-side. A real, previously-unnamed case this pass surfaces: `contentEditorUnlocked` can be true while `exportData.snapshotEligibility.eligible` is false — a manual Blueprint edit (BD5) creates a new `draft` Blueprint version without moving `projects.status` backward, so the tab stays open while there is, for a moment, no approved Blueprint to export against. This is the **first** state the tab must check, before even looking at the QA gate (§2 below) — discussing QA readiness is meaningless if there is no valid lineage to export yet.

### 2. Export status (requirement 2)

**Six named states, each rendered from `exportData` fields alone — no client-side gate/staleness recomputation, ever:**

| State | Condition (all from `exportData`) | Primary message |
|---|---|---|
| **Snapshot not ready** | `snapshotEligibility.eligible === false` | `snapshotEligibility.reason` verbatim (e.g. "The current Blueprint version is not approved."), with a link to the Blueprint tab. |
| **Blocked — No QA** | `gate.decision === 'blocked' && gate.reason === 'no_qa'` | "Run QA before exporting." |
| **Blocked — QA stale** | `gate.decision === 'blocked' && gate.reason === 'stale'` | `qaStaleReason` verbatim (already the exact human-readable sentence `computeQaStaleness()` produces — reused, not reworded a second time). |
| **Blocked — QA failed** | `gate.decision === 'blocked' && gate.reason === 'fail'` | "N finding(s) must be resolved before export," linking to the QA tab's category cards (never duplicating finding detail here, matching the QA-UI plan's own §6 instruction). |
| **Allowed — Verified** | `gate.decision === 'allowed' && verificationTier === 'verified'` | "Ready to export — QA verified." |
| **Allowed — Partially verified** | `gate.decision === 'allowed' && verificationTier === 'partially_verified'` | "Partially verified — N of 9 QA categories evaluated" (§6). |

Every one of these six states is a pure `switch`/lookup over already-computed `exportData` fields — no new query, no re-derivation, matching requirement 2's explicit "use the existing gate logic, do not duplicate it in the UI."

### 3. Verification tier display (requirement 3)

Reuses `StatusBadge` unmodified (zero new components, matching QU10's own "100% reused" precedent) — and because `StatusBadge` already renders a text label alongside its color, "do not use color alone" is satisfied by construction, not by a special case:

- **Verified** — `success` tone, label "Verified."
- **Partially verified** — `warning` tone, label "Partially verified," always paired with the "N of 9 categories evaluated" sentence (§6) in the same breath, never the badge alone.
- **Unverified** — `danger` tone, label "Unverified," **always** paired with an explanatory sentence, not just the badge: on the confirmation modal (§8) and on the success state (§9) alike, the literal sentence "Exported without a passing QA review" appears next to the badge every time `qa_bypassed = true` is the reason a result is Unverified — this is the concrete answer to requirement 3's "make Unverified especially clear when ED12 bypass is used."

### 4. Format selection (requirement 4)

- **Checkboxes, not radio buttons or a select** — matches Design V1 exactly and ED7 (multiple formats may be requested in one export action; the user is not limited to one format at a time).
- **Default selection: Markdown only.** Not all four — DOCX in particular carries real per-call generation cost (§5 of this document), and defaulting to the heaviest format for every export would be wasteful for the common case. Markdown is the cheapest, most universal format and the most likely first choice; a user who wants more explicitly checks more. This is the concrete "favor the simplest V1 workflow" answer the task asks for.
- **Format availability while formatters are incomplete:** each checkbox is independently enabled/disabled based on whether that format's generator has actually shipped (an implementation-time capability flag, not a schema or gate concept) — an unshipped format renders disabled with a "Not yet available" label, never hidden entirely (a user should always see all four named formats exist, per Design V1's own frozen list, even before every generator ships). The Export action itself requires at least one *available* format checked — the same "disabled until ≥1 valid selection" discipline already used for the Customize-QA checklist's "Run selected" button (QU11).
- **One action, any number of checked formats** — not one-format-at-a-time; a single "Export" click generates every checked format in one `exports` row with N `export_files` rows (ED7, unchanged).

### 5. Normal export (requirement 5, Allowed state)

Shown: the verification badge+text (§3), the format checklist (§4), and a single "Export" button. **No confirmation modal.** A normal export is non-destructive and insert-only (ED8) — it creates new, permanent rows and never touches, deletes, or overwrites anything; there is no meaningful destructive/irreversible concern the task's own "no modal unless destructive" rule would require guarding against. One click moves directly to the running state (§9).

### 6. Partial QA (requirement 6)

An informational banner, not a blocking or friction-adding one: **"Partially verified — N of 9 QA categories evaluated,"** immediately followed by the skipped categories named inline (reusing the exact locked category labels from QU11, e.g. "Skipped: `intent`, `factual`"). The Export button remains fully available, identical interaction to §5's Verified state — **no additional confirmation step**, clarifying (and superseding) the heavier "one-step lightweight acknowledgment" language in ED13's original LEAVES-03 draft section: this task's own explicit instruction ("Normal Export remains available according to ED13... without being blocked unnecessarily") resolves that earlier ambiguity in favor of the simplest workflow — inform, don't gate. ED13's actual locked wording (LEAVES-04) never mandated a confirmation step either; this was always the correct reading, now made explicit in the UI spec.

### 7. Blocked export (requirement 7)

Every blocked state (§2's Blocked-* rows) shows: the reason-specific message, a **"Review QA"** action (navigates to the QA tab, reusing the QU4 cross-tab navigation pattern already built), and a secondary **"Export without QA"** action (§8). **The normal Export button/action is entirely absent in a blocked state** — never rendered disabled-with-a-tooltip, simply not present, so there is no path (UI trick, hidden parameter, or otherwise) that could be mistaken for silently enabling it. The only way to produce a file from a blocked state is the explicit bypass flow.

### 8. ED12 bypass (requirement 8)

Clicking "Export without QA" opens a confirmation modal — **locked copy, exact wording:**

> "This content has not passed a current QA validation. The exported file will be marked Unverified."
>
> **[Cancel]** **[Export without QA]**

Confirming calls the export action with an explicit `bypassRequested: true` argument — never a default, never inferred, never toggleable via a query string or hidden field. `authorizeExport()` (already implemented, EXPORT-02, unmodified) re-verifies server-side that the gate is actually Blocked before honoring the request, exactly as already locked — this UI spec adds no new server trust, only the one confirmed client action that supplies the flag. Canceling returns to the Blocked state (§7) with nothing sent to the server — no export attempt, no row written.

### 9. Export result (requirement 9)

Four states, matching `export_status` (`idle`/`running`/`done`/`failed`, ED8, unchanged):

- **Idle** — the pre-export state described in §5/§6/§7 above (format selection + action, or the blocked reason).
- **Running** — a spinner/progress state (Design V1's own language), shown for the (typically brief, no-AI-call) duration of generation.
- **Success** (`done`) — for each requested format: a download link (a signed URL generated at render time from `export_files.storage_path`, never a permanent public link, §10 of this document, unchanged), the format name, and — once per export, not once per format — the **verification tier the export was actually created with** (frozen at export time, read from the completed `exports` row, never re-derived from the project's *current* state, which could have moved on since) and the creation date/time (`requested_at`/`completed_at`). Per requirement 3, a `qa_bypassed = true` result repeats the "Exported without a passing QA review" sentence here too, not only on the confirmation modal.
- **Failed** — a plain error banner with a retry action that starts a **new** export request (ED8's all-or-nothing design, unchanged — never a "resume the failed row" action).

**No export-history dashboard.** §9's original planning-pass text recommended a full history list as cheap and worth building; this lock narrows that: at most a compact "recent exports" list (a handful of rows, no pagination, no filtering, no separate page) is in scope for a first build, and only if it costs nothing beyond a single already-cheap query — the task's explicit "do not build a large export history dashboard" takes precedence over §9's earlier, more expansive recommendation where the two differ.

### 10. Toyota (requirement 10)

- **Zero new DB queries for status/gate/tier display** — every field §2/§3/§6 render already exists on `exportData` (EXPORT-03); the UI is a pure projection of already-fetched server state.
- **No client-side recomputation of gate or staleness** — `computeExportGate()`/`computeQaStaleness()` are never called from client code; the UI trusts `exportData.gate`/`exportData.qaStale`/`exportData.qaStaleReason`/`exportData.verificationTier` as-is, the same "server computes, client renders" discipline already used everywhere else in this app (QA tab, Content Editor, Blueprint Review).
- **Format checkbox state is local, ephemeral client UI state** (`useState`) — no query, no server round-trip until the Export action itself fires.
- **Files are generated only on explicit Export click** — never pre-generated, never generated speculatively while a user is still choosing formats.
- **A "recent exports" list (§9), if built, is one additional query** — deferred to implementation time, added only if genuinely cheap (today, zero `exports` rows exist for any project, so the query costs nothing to add and nothing to render).

### 11. Development cleanup (requirement 11)

The temporary manager-only **"DEV — Export data (Phase 4.7 foundation)"** debug panel added in EXPORT-03 (a collapsed `<details>`/`<pre>` JSON dump in the workspace sidebar) is verification scaffolding only, matching this project's own established "DEV TEST CONTROL" convention (`generation-test-controls.tsx`, the now-superseded `/api/dev/run-qa` route). **It must be removed as part of the Export tab's real implementation**, once the tab itself can display everything the debug panel exists to expose today — flagged here so it is not mistaken for a permanent feature or accidentally shipped alongside the real UI.

## Key risks, ranked

1. **ED2's gating-function extraction is the single most important correctness dependency in this phase.** If implementation quietly re-derives staleness logic for Export instead of extracting and reusing QA's existing computation, the two will drift the first time either is edited without the other — precisely the failure mode this document was told to design against. This should be the first concrete implementation step, before any Export UI is built on top of it.
2. **ED1 (`exports.qa_report_id`) is a required schema change, not optional polish** — without it, an export has no durable, permanent record of which QA report actually authorized it, the same class of gap as every prior phase's own flagged lineage column (BD1, CD3, QD1). Should land before any export-triggering code is written, same urgency class as those three.
3. **DOCX is the one format genuinely different in kind from the other three** — Markdown/HTML/JSON are all text transforms of data already fully in-process; DOCX requires a new dependency and real (if modest) document-building work. If DOCX proves meaningfully harder to get right than this document estimates (heading-style fidelity, list-numbering correctness across nested levels), the honest fallback is to ship Markdown/HTML/JSON first and treat DOCX as a fast-follow, not to let DOCX's complexity block the other three formats' straightforward release.
4. **§8's "no partial success" all-or-nothing status design is a real product tradeoff, not free** — a document that successfully generates 3 of 4 requested formats but fails on DOCX loses all 3 successful outputs under this document's recommended design. This is deliberately conservative (matching Design V1's binary success/failure framing) but is worth flagging as a real, opinionated choice a future revision could reasonably reverse if partial success turns out to matter in practice.
5. **ED12 (Export bypass, see the dedicated section above) is the sharpest risk in this whole document, precisely because it is a deliberate, locked hole in an otherwise-strict gate.** If `qa_bypassed` is ever forgotten in a UI surface (a history row, a downstream integration reading `exports` directly) the whole point of ED2's strict gate is undermined silently. This is exactly why ED12 requires the flag to be checked and rendered everywhere an export's status is shown, not just at creation time — worth extra scrutiny at implementation time, since locking the *decision* here does not by itself guarantee a correct *implementation* of it.
6. **ED13's "lighter confirmation for partial, heavier confirmation for bypass" distinction is a UX judgment call that depends on users actually reading either one** — if the two confirmation steps end up looking too similar in practice (same modal shape, different word), the deliberate asymmetry in stakes this locked decision argues for could collapse into "just another dialog to click through," undermining requirement H's "never silently" goal by habituation rather than by design. Worth explicit visual differentiation at implementation time, not just different copy — a locked decision does not by itself guarantee a correct implementation of it (mirrors the same caveat already recorded for ED12's `qa_bypassed`, risk 5, above).
7. **ED14's "snapshot not ready" state (§1 of the Export Tab UI section) is easy to skip if implementation jumps straight to the QA gate** — a manual Blueprint edit (BD5) can leave `contentEditorUnlocked` true while `exportData.snapshotEligibility.eligible` is false, a real, previously-unnamed case this pass surfaced. An implementation that only checks the QA gate would either crash or show a misleading blocked-QA message when the actual problem is an unapproved Blueprint edit — this must be checked first, explicitly, not assumed away.
8. **§10's rejection of a checksum column is a judgment call, not a certainty** — if Storage-layer corruption is ever actually observed (unlikely, given zero prior incidents across every other stage's Storage usage in this pipeline, but not provably impossible), this decision should be revisited with real evidence rather than assumed permanently correct.

## Explicitly out of scope

- **Actual export code, migrations, or Storage writes** — this document is planning-only, per the task's own explicit constraint.
- **A checksum column on `export_files`** (ED10) — rejected, not deferred-as-a-maybe, for the stated reason (no demonstrated need anywhere in this pipeline's Storage usage).
- **A per-format-partial-success status model** (§8) — the all-or-nothing design is the V1 default; a partial-success model is a legitimate future revision if real usage demonstrates a need, not designed further here.
- **CMS-specific export targets** (WordPress publishing, a specific headless-CMS payload shape) — Design V1 freezes the four formats (Markdown/HTML/DOCX/Structured JSON) only; a CMS integration is a distinct, later, unscoped question.
- **Export scheduling, batch/bulk export across multiple projects, or an export API for external consumers** — this phase covers exactly Design V1's single-project, human-triggered Export tab, nothing broader.
- **Semantic/embedding-based document diffing between exports** — not needed; ED8's immutable-snapshot model already makes every export independently inspectable without needing to diff against a prior one.
- **A `generation_runs` row for every real export** — explicitly rejected as the default (ED4); the narrow audit-log-only exception discussed in §8 is not proposed as a requirement.
- **Rich formatting fidelity beyond what the source Markdown already expresses** — Export renders exactly what `content_versions.body` already contains; it does not add new formatting the writer never specified (no auto-generated table of contents, no auto-inserted images — Image Suggestions remain Phase 4.5 Appendix A's own separate, unimplemented concern, untouched by this document).
