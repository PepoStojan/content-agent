## Evidence-awareness rules (locked, cross-cutting — apply to `factual` and, where relevant, `intent`)

Stated explicitly and separately because they cut across multiple sections above rather than belonging to one QD entry alone:

- **QA is evidence-aware, not evidence-blind.** `factual` QA never judges a section's claims in a vacuum — it is always given the section's own supplied evidence as context, per the next rule.
- **`factual` QA receives the exact same relevance-filtered evidence packet the writer had access to for that section** — the same deterministic, capped `research_sources` subset produced by `lib/generation/content/evidence.ts` (Phase 4.5 CD2), recomputed fresh, not re-imagined or widened. This is what makes a `factual` finding fair: the reviewer is held to the same evidentiary boundary the writer was.
- **QA must not evaluate claims against external knowledge that was not supplied to the system.** The model's own general/world knowledge is not a legitimate basis for a `factual` finding — only the section's actual supplied evidence packet (and, for a manually-edited section with no generation provenance, the freshly-recomputed evidence packet per §2) may ground a finding. A claim the model merely knows to be plausible or true from training data, with nothing in the supplied evidence to back it, is not verified by that outside knowledge — it is exactly the "insufficient evidence" case, handled per §4/§7's severity rules, not waved through because the model happens to know better.
- **QA must not invent findings.** Every finding above PASS requires a real, locatable quote from the actual evaluated text (QD7) — a finding is never asserted on the reviewer's own judgment alone, unattached to a real substring of what it was given to evaluate.

## 0. What a QA run inspects, precisely (Question 1–3)

**A QA run is one bounded evaluation pass over a project's Content, represented by exactly one new `qa_reports` row** (produced by one `generation_runs` row of type `qa_run`), pinned at creation time to three exact things — never re-resolved dynamically later, same discipline as every prior phase's lineage pinning:

- `qa_reports.brief_version_id` — the exact `brief_versions` row current for the project at run time.
- `qa_reports.blueprint_version_id` — the exact `blueprint_versions` row current at run time.
- `qa_report_content_versions` rows — one per leaf Blueprint node, each pointing at that section's exact `content_versions.id` current at run time.

**It inspects both the whole assembled article and individual sections, deliberately — not one or the other.** Some of the 9 categories are only meaningful at whole-document scope (`intent` — does the *entire piece* serve the Brief's search intent; `structure` — does the *overall* heading tree make sense, no orphan/duplicate sections). Others are only meaningful per-section (`topics`/`entities`/`links`/`brand`/`style`/`forbidden_chars`/`factual` — each concerns one leaf section's own assigned scope and own body text). A category is never evaluated at both scopes at once; §2 fixes each category's scope exactly once.

**A real gap this pass found, not assumed:** the approved Blueprint's node tree is the source of truth for *which* leaf sections should exist. QA must enumerate that full expected set (from `blueprint_nodes` where `parent_id`/children make it a leaf, scoped to the current approved `blueprint_version_id`) and treat any leaf node with **no** `content_documents` row yet as its own finding (`structure`, WARN if some sections are done and some aren't, or a plain incompleteness note) — not silently iterate only whatever `content_documents` rows happen to exist. A naive "loop over existing content" implementation would silently pass an incomplete document with zero warning, which is exactly the kind of false negative this planning pass was asked to hunt for.

## 1. Category → method → scope (Questions 4, 5, 19 — QD3)

| Category | Method | Scope | What it checks |
|---|---|---|---|
| `intent` | **LLM** (1 call, whole-run) | Whole document | Does the assembled article, read as a whole, actually serve the Brief's `search_intent_label`/`content_objective`/`target_audience`/`unique_value`? The one category that is inescapably a judgment call — no deterministic proxy is honest here. |
| `topics` | Deterministic | Per section | For each leaf node, do its assigned `blueprint_nodes.entities` (Blueprint's own already-traceability-validated subset, BD3) appear, in some recognizable form, in that section's current body? Keyword/phrase presence check, same class of matching already proven for Content's own evidence relevance filter (Phase 4.5 §4) — not semantic, not LLM-judged. |
| `entities` | Deterministic | Per section | Same mechanism as `topics`, applied strictly to named entities (proper nouns / specific terms in the `entities` array) rather than the broader topical goal — a real, separate frozen category, so kept as a separate check even though it reuses the same matching primitive. |
| `structure` | Deterministic | Whole document | Heading hierarchy matches the approved Blueprint's tree order/levels; every leaf node has exactly one `content_documents` row (§0's gap); no duplicate/orphaned headings; each section's word count is within Blueprint's WARN-level band (reuses the same ±15% pattern already live in the Content Editor's word counter, Phase 4.5's live-verified UI feature — not reinvented). |
| `links` | Deterministic | Per section | **Re-validates** (does not assume-still-valid) that every Markdown link in the section's *current* body resolves to that node's own `internal_link_targets` whitelist — the same check `lib/generation/content/links.ts` already performs at AI-generation time, re-run here because manual Edit bypasses it entirely (QD2). |
| `brand` | Deterministic | Per section | **Re-runs** `assertBrandCompliance` (forbidden phrases / prohibited claims) against the section's current body — same QD2 rationale: this already exists and is reused unmodified, just triggered from a new call site. |
| `factual` | **LLM** (1 batched call, whole-run) | Per section (one call, N findings) | Does each section's claims stay within what its own supplied evidence packet actually supports? See §4/§13 for exactly how this is bounded and kept honest. |
| `style` | Deterministic | Per section | Readability/repetition heuristics only — sentence-length distribution, passive-voice ratio, literal repeated-phrase detection across sections (the deterministic near-duplicate check Phase 4.5 §6/§21 explicitly deferred as "a real future QA-category candidate" — this is that candidate, arriving on schedule). Deliberately **not** an LLM "does this sound good" judgment — that would be exactly the vague AI quality score this document was told to avoid. |
| `forbidden_chars` | Deterministic | Per section | **Re-runs** `assertNoEmDash` against the section's current body — same QD2 rationale as `links`/`brand`. |

**7 of 9 categories are deterministic; only `intent` and `factual` need Claude.** This is not a stylistic minimalism choice — it's the direct answer to "use deterministic checks wherever deterministic rules are possible" (this task's own instruction): every category with an objectively checkable rule (a link either is or isn't in the whitelist; an em dash either is or isn't in the string) stays deterministic; only the two categories that are genuinely matters of judgment (does this serve the intent; is this claim actually supported) go to the model.

## 2. Inputs to LLM QA, and how much research it sees (Questions 6, 7)

**`intent` (1 call):** the full assembled article (CD6's existing computed-on-read function — reused unmodified, no new assembly logic) + the pinned Brief version's `search_intent_label`, `search_intent_rationale`, `content_objective`, `unique_value`, `target_audience`. **No research evidence at all** — intent-matching is a Brief-vs-content comparison, not an evidence-vs-content one; supplying research here would be pure token cost with no signal.

**`factual` (1 batched call):** for every leaf section, the same capped, per-section relevance-filtered `research_sources` subset Content generation itself was given (`lib/generation/content/evidence.ts`, reused unmodified — same deterministic keyword/entity-overlap filter, same cap) + that section's current body + (if it exists — see below) the `evidenceUsed` array from the `content_versions` row's originating generation, read back from Storage exactly the way the Content Editor UI already does today. One structured tool-use call returns one finding per leaf section in a single response — never N separate calls (QD4).

**A real asymmetry worth naming:** a manually-edited section (CD5) has `generation_run_id = null` — there is no `evidenceUsed` to read back for it, by construction (§11 of the Phase 4.5 plan: an edit has no generation provenance at all). For those sections, `factual` QA still runs (using the same relevance-filtered evidence, recomputed fresh — evidence filtering has no dependency on a generation having happened), it just has one fewer signal available (no self-reported `evidenceUsed` to sanity-check against); the LLM is told this explicitly in the prompt ("this section was manually edited; no self-reported evidence references exist") rather than silently treating a missing field as a violation.

## 3. Findings storage — the real schema gap (Question 9, QD1)

**As shipped, `qa_findings` cannot represent "this specific finding is about this specific section."** It has `qa_report_id`, `category`, `method`, `status`, `note` — no version/section anchor at all. `qa_report_content_versions` proves *which* content versions a report as a whole looked at, but a `topics` finding and a `factual` finding both attached to the same `qa_report_id` are otherwise indistinguishable in terms of which of N sections they're actually about, once a document has more than one section — which is every real document.

**Required (not created here): `qa_findings.content_version_id uuid references content_versions(id)`, nullable.** Populated for every per-section category (`topics`, `entities`, `links`, `brand`, `factual`, `style`, `forbidden_chars`); left `null` for the two whole-document categories (`intent`, `structure`). No second `blueprint_node_id` column is needed alongside it — `content_versions.blueprint_node_id` already exists on the referenced row, so `content_version_id` alone is sufficient to resolve "which section" without a redundant FK.

This is the same class of gap Blueprint (`brief_version_id`) and Content (`blueprint_node_id` on `generation_runs`) each found and fixed in their own planning passes — flagged with the same discipline: a precise column, a stated reason, no migration written by this document.

## 4. Severity model — what PASS/WARN/FAIL means per category (Question 20)

No single blended score exists anywhere (Design V1 rule #6, unchanged) — `qa_reports.overall_status` is a pure deterministic rollup over `qa_findings.status`: **FAIL if any finding is `fail`, else WARN if any finding is `warn`, else PASS.** Method (`deterministic`/`llm`) never changes how a status counts toward the rollup — a FAIL is a FAIL regardless of which method produced it, which is what keeps "no blended score, no method secretly weighted differently" actually true rather than just asserted.

Within a category, the general severity philosophy:

- **Guard-rail violations re-detected at QA time** (`links`, `brand`, `forbidden_chars` finding something that Content's own generation-time checks would have hard-failed on) → **FAIL.** These are objectively checkable and would have blocked generation itself had the same text come from the AI path — QA re-detecting them on manually-edited text should be exactly as strict, not softer (QD2).
- **Coverage/completeness gaps** (`topics`/`entities` missing an assigned item, `structure` finding an ungenerated leaf section) → **WARN** by default, escalating to **FAIL** only for total absence (a section with zero of its assigned entities present, or a leaf node with no `content_documents` row at all when the project claims Content is otherwise complete).
- **`intent`** → WARN for a partial/weak match, FAIL only for a clear mismatch (e.g., the Brief's intent is transactional/comparison but the article reads as a generic definitional piece) — this is the one category where "FAIL" should be reserved for something a human would agree with at a glance, precisely because it's the most judgment-heavy category in the whole set.
- **`factual`** → **WARN is the default outcome for anything short of an unambiguous, quotable fabricated specific** (a concrete number, price, URL, or named-competitor claim the supplied evidence packet does not contain). This is a deliberate, narrow FAIL bar (§13, QD7) — the alternative (any judgment-call flags a hard Export-blocking FAIL) would make the single most hallucination-prone category in this design also the single most consequential one, which is the opposite of what a careful design should do.
- **`style`** → WARN only; this category is a quality signal, not a trust violation (mirrors Blueprint's BD4 word-count-sanity reasoning exactly — a stylistic wobble should never block Export on its own).

Exact numeric thresholds (how many missing entities constitute FAIL vs. WARN, the sentence-length band for `style`) are an implementation-time tuning question, not fixed by this document — same treatment Blueprint gave its own word-count band (BD4: "exact bounds are an implementation-time product decision, not specified here").

## 5. Lineage pinning and staleness (Questions 8, 11, 12, 13 — QD6)

**Pinning at run time** answers Question 8 completely: `qa_reports.brief_version_id`/`blueprint_version_id` are captured from whatever is actually current *at the moment the QA run starts*, written once, never re-resolved — identical discipline to Blueprint pinning its `brief_version_id` and Content pinning its Blueprint-node lineage. `qa_report_content_versions` does the same for every leaf section's content version. A QA report therefore always knows exactly what it evaluated, permanently, even if every one of those things later changes.

**What happens on edit/regenerate (Questions 12, 14):** CD5 already guarantees Content edits/regenerates are insert-only — a new `content_versions` row, old ones untouched. The existing QA report is **not** mutated, deleted, or auto-invalidated (no silent cascade — the same principle already stated explicitly for Blueprint-after-Brief-regeneration, Phase 4.4 §9, and Content-after-Blueprint-regeneration, Phase 4.5 §15). It simply becomes checkable-for-staleness: compare each `qa_report_content_versions.content_version_id` against `content_documents.current_version_id` for the same `blueprint_node_id` — any mismatch means that section changed since this report ran.

**Why staleness must gate Export, not just display a badge (Question 13, QD6):** Design V1 rule #8 says "Export is blocked while any QA category is FAIL" — read literally against a stale report, a project could show a green PASS banner while the actual current text (edited after that PASS was recorded) has never been checked at all. That's a worse failure mode than showing no QA result, because it's confidently wrong rather than honestly absent. **Resolution:** the Export-blocking check must ask three questions, not one — "does the latest report have any FAIL," "is the latest report's pinned content-version set identical to the current one for every leaf section," and "is the latest report's evaluated leaf set identical to the current approved Blueprint's leaf set" (QD6's locked clarification) — and treat a stale report (by either test) the same as no report for gating purposes (blocks Export, or at minimum surfaces "QA is out of date, re-run before exporting" with equivalent force to a FAIL banner). This is a real design decision this planning pass is making, not merely restating the frozen design doc, because the frozen design doc was written before staleness was a reachable state (QA didn't exist yet when it was authored).

**The leaf-set staleness case, why it's a distinct check from content-version staleness:** if a Blueprint's current approved version changes after a QA report ran — via whole-document AI regeneration (Phase 4.4 BD2) **or via manual Blueprint editing (Phase 4.4 BD5)** — a new `blueprint_versions` row with an entirely new `blueprint_nodes` snapshot is created either way (BD5 is versioned identically to BD2 for exactly this reason: so QA's staleness detection doesn't need a third case). The *old* leaf nodes the report evaluated may no longer exist at all in the current Blueprint, or new/changed leaf nodes may now exist that the report never saw. Comparing pinned `content_version_id`s alone cannot detect this — those rows still exist and are still valid content, they're simply no longer the full, current picture. The leaf-set check (report's evaluated `blueprint_node_id` set vs. the current approved Blueprint's leaf set) is what catches this case regardless of which of the two triggers produced the new version; content-version-id comparison alone would miss it.

**Note this also means a BD5 manual Blueprint edit — even one that changes no leaf's `entities`/`internal_link_targets`/etc., only e.g. a `title` typo fix — still invalidates prior QA leaf-set alignment**, because BD5 always produces a genuinely new `blueprint_versions` row (never an in-place update), and QD6's leaf-set check compares *version identity*, not a field-level diff of what actually changed. This is a deliberately conservative, safe-by-default choice — the alternative (attempting to distinguish "cosmetic" Blueprint edits from "substantive" ones before deciding whether to invalidate QA) is exactly the kind of judgment call this deterministic staleness check is designed to avoid making.

**Note (2026-08-20, LEAVES-01 through LEAVES-04) — locked additions at Export's own layer, recorded here only for cross-reference:** `docs/architecture/phase-4-7-export-plan.md` documents **ED12 ("Export without QA") and ED13 (Export provenance tiers), both locked 2026-08-20** — ED12 is an explicit-bypass path for FAIL/stale/no-QA states; ED13 extends the gate's output to distinguish a full-QA export ("Verified") from a QD9 partial-QA export ("Partially verified"), still both requiring a current, non-FAIL report. Neither changes QD6 itself — the normal Export gate (§6 of `phase-4-6-qa-ui-plan.md`, implemented as `computeExportGate()`) still blocks exactly as designed on a stale or FAILing report, full or partial, and the gate remains the one deterministic function (ED12 requirement 10 / ED13 — bypass and tiering are never a second gating algorithm). A stale, FAILing, or no-QA state — regardless of full or partial coverage — reaches export only through ED12's unchanged bypass, never through ED13's Verified/Partially-verified tiers, and never rendered as if it were a passing QA result (`exports.qa_bypassed = true` never means QA passed). Locked architecture, not yet implemented.

**Confirmed live, not just theoretical (2026-08-20):** the first real Phase 4.6 QA execution against a BD5-edited project hit exactly this case end to end — a single-node Blueprint edit had orphaned all 22 leaf sections' Content standing (see Phase 4.4 plan's new §19/BD6 for the full product-level analysis of *why* this happens and whether it's the right behavior — confirmed correct, an intentional consequence of BD5, not a bug). QA correctly reflected reality rather than silently passing or crashing: the deterministic `structure` category reported `fail` ("No leaf sections have generated content yet"), `factual` correctly made zero LLM calls (nothing to batch), and the one `intent` finding that was returned got correctly rejected under QD7 because its "quote" was placeholder scaffolding text, not real evaluated content. This is the staleness/leaf-set-change discipline working exactly as designed against real data, not merely a paper argument.

## 6. Re-run behavior and finding resolution (Questions 15, 16, 17, 18, 21 — QD5)

**QA never approves anything (Question 15).** No `qa_reports.approved_by`/`approved_at` exists, and none is proposed — this matches Design V1 exactly (the QA tab has no Approve action, only "Re-run validation" and an Export-blocking banner) and the general pipeline principle that a report is a diagnostic snapshot, not a gate a human affirmatively signs off on the way they do Brief/Blueprint. **Human interaction (Question 16)** is limited to: trigger a run, read the category list, click "Re-run validation," and — once no FAILs remain and nothing is stale — proceed to Export. There is no separate "QA approval" workflow to design because Design V1 never specifies one.

**Findings are not individually resolved (Questions 17, 18, 21).** No per-finding dismiss, override, or "mark as false positive" action exists in Design V1, and none is proposed here — building one would be exactly the kind of structure "Design V1 never asked for" this document was told to watch against (mirrors Phase 4.5 §12's own reasoning for rejecting a per-section Request-Changes state). The only correction path for any finding, true or false-positive alike, is: go fix the underlying section (Edit or Regenerate), then trigger a fresh whole-report "Re-run validation." **Re-running is always whole-report** — a new `qa_reports` row, a fresh full pass over every category (QD5) — never a per-category or per-finding partial re-run, which would reintroduce exactly the kind of "is this report internally consistent" bookkeeping problem the insert-only, immutable-snapshot model exists to avoid.

**If LLM false-positive rate turns out meaningfully high in practice**, the honest next step is tightening QD7's quote requirement or narrowing the `factual`/`intent` FAIL bar further (§13) — not adding a dismiss button that lets a human silently override a report without it being reflected in the persisted record. Flagged as a real, named risk below, not solved preemptively.

## 7. Preventing hallucinated findings (Question 22 — QD7)

Layered mitigations, mirroring the discipline Content's own §7 already established for the opposite direction (preventing the *writer* from fabricating) — applied here to prevent the *reviewer* from fabricating:

1. **Forced tool-use schema requiring a literal quoted excerpt** for any finding above PASS — a `quote` field that must be a locatable substring of the actual text supplied for that section/document. A finding whose `quote` doesn't resolve to real text is a validation failure, not a persisted finding — same "response validation rejects the impossible" discipline already proven for Blueprint's entity-traceability check (BD3) and Content's internal-link whitelist.
2. **The same prompt-injection/reference-data framing used everywhere else** in this pipeline — the content being reviewed, the Brief fields, and the evidence packet are all explicitly delimited as data to evaluate, never instructions to the reviewer about its own behavior.
3. **A deliberately narrow FAIL bar for both LLM categories** (§4) — WARN is the default outcome for anything short of an unambiguous, quotable violation, which means an LLM false positive most often costs a yellow badge a human can dismiss by reading the quote, not a hard Export block.
4. **Evidence parity check:** `factual` QA is given the exact same relevance-filtered evidence packet Content generation itself used for that section (recomputed via the same deterministic filter, not re-imagined) — this prevents the reviewer from judging a section "unsupported" against evidence the writer was never actually given, a distinct and real failure mode a naively-designed QA pass could introduce.
5. **Everything is inspectable against a permanently pinned exact version** (§5) — a human reviewing a suspicious finding can always pull up the exact `content_versions.id` it was made against and check the quote directly; nothing is judged against "whatever the content currently says."

## 8. Race conditions and concurrency (Question — Sherlock requirement)

**Resolved by construction, not by new locking code.** Because `content_versions` is strictly insert-only (CD5) and a QA run pins the exact `content_versions.id` set it read *at input-assembly time, before either LLM call is made* (§5), a concurrent Edit/Regenerate landing mid-run cannot corrupt the report — the report simply ends up pinned to whatever was current at the moment it started reading, which is always a real, valid, previously-current state, never a torn/partial one. The only consequence of a race is that the finished report may already be stale by the time it's displayed — which is exactly the staleness case §5/QD6 already designs for, not a new problem needing its own mechanism.

**Two QA runs racing each other** for the same project is prevented the same way Phase 4.2's D2 already prevents every other duplicate-generation race: the existing partial unique index (`(project_id, type) WHERE status IN (...)`) applies unmodified to `type = 'qa_run'` — QA has no per-section scoping need the way `content_generate` did (CD3), because a QA run is inherently one whole-project, whole-document unit, so **no schema change is needed here** (worth stating explicitly, since it would be easy to reflexively assume every new generation type needs its own CD3-style node-scoped index — it doesn't; that need was specific to Content's per-section concurrency model, not a general rule).

## 9. Cost control (Question 23, QD4 — AMENDED 2026-08-20, LEAVES-04)

**Maximum 2 LLM calls per QA run, determined by which categories are selected (QD9), never more:** `intent` selected → exactly 1 whole-document call; `factual` selected → exactly 1 batched call covering every evaluated leaf section's grounding in a single structured response, never N separate calls; neither selected → 0 Anthropic calls; both selected → 2, same as the original design. **Deterministic-only QA (any subset of the 7 non-LLM categories, with neither `intent` nor `factual` selected) must not call Anthropic at all.** This is the direct, load-bearing reason Partial QA (QD9) is a real cost/time control, not just a smaller report — a user who only wants to re-check `entities`/`links`/`brand` after a manual edit now pays zero AI cost to do it. The batched, never-per-section shape of `factual` is unchanged from the original design — only whether either call happens at all is now conditional. Full QA (all 9 categories, still the unchanged default) costs exactly 2 calls, identical to before this amendment — nothing about the flat-cost-relative-to-document-length property changes; this amendment adds cheaper cases, it does not make the existing case more expensive or less predictable. **No automatic QA** — QA runs only on an explicit user trigger (initial run, "Re-run validation," or a "Customize…" partial run), never automatically on every Content edit/regenerate; this directly closes Phase 4.2's own flagged, still-open risk #4 ("AI QA re-run cost... no cooldown or guard... no visibility into accumulating cost") rather than inheriting it unaddressed into the first real QA implementation.

## Confirmed implementation finding: Markdown formatting can defeat literal entity/topic matching (fixed 2026-08-20)

Found by running a real deterministic QA audit against project `64f3a6aa-3090-457a-ae54-3a1d506a87d2`'s live content, not hypothesized in advance. The manually-edited "Step 3: Crowded Bar Test" section's body reads `The **crowded** bar test is simple...` (a real Content Editor Markdown-toolbar Bold edit, CD5). The `entities` check's literal case-insensitive substring match against the assigned entity `The crowded bar test` **failed** — not because the topic is actually missing (it plainly isn't; the whole section is about the crowded-bar test), but because the inserted `**` characters split the phrase mid-string, so the raw body no longer contains the literal, unbroken substring `the crowded bar test`.

**This was a real false negative in the shipped `topics`/`entities` checks, not a hypothetical edge case** — confirmed by directly reading the stored body, not assumed. **Fixed**: both checks now match through `normalizeForMatching()`/`containsNormalized()` (`lib/generation/qa/text.ts`), which strips Markdown syntax (emphasis/strikethrough/inline-code delimiters, link/image brackets, heading/list markers) from a throwaway copy of the text used only for comparison — the stored and rendered body are untouched. This is intentionally narrow: syntax removal only, no stemming, no synonyms, no fuzzy/semantic matching, no embeddings — a genuinely absent entity still fails to match after normalization, verified directly against the same project (the Step 5 section's `entities` FAIL, where none of its 4 assigned entities are present in any form, is unchanged by this fix).

**Why this matters beyond the one section it was found in:** any section written or edited through the Content Editor's own Markdown toolbar (Bold/Italic/H2/H3/lists/links — all five already live-verified in Phase 4.5) can trigger the same failure mode wherever formatting happens to land inside an assigned entity or a significant title term. Left unfixed, this would have produced misleading `entities`/`topics` findings on ordinary, correctly-formatted content — a systematic false-negative source, not a one-off. Recorded here as a genuine, evidence-based architecture finding (not merely "flagged as a risk") because it was caught by actually running the checks against real data, exactly the kind of gap a planning-only pass could not have found.

## Confirmed implementation finding: entity aliases were matched too strictly (fixed 2026-08-20, LEAVES-01)

Found running a real deterministic QA audit against project `ce718b4d-25e1-40f6-9af5-9716c7ce1aa0` ("how to make spageti bolognese"). A Blueprint-assigned entity of the shape `"Bolognese sauce (ragu alla bolognese)"` — primary term plus a parenthetical alias, a real authoring convention this Blueprint used repeatedly — was matched by the pre-fix `entities` check as **one single literal string, alias included**. A section whose body plainly used the concept (in one real case, the body used the Italian alias "ragu alla bolognese" without the English "Bolognese sauce" phrase; in others, neither term appeared at all) was reported identically as "missing," with no way to tell a section that genuinely never mentioned the concept apart from one that covered it under a different name than the matcher happened to require verbatim.

**Fixed, deterministic, no LLM, no embeddings, no broad fuzzy matching:**

- `parseEntity()` (`lib/generation/qa/text.ts`) splits a trailing `"(...)"` on an entity string into `primary` + `aliases[]` (comma/semicolon-separated). An entity with no parenthetical is returned unchanged (`aliases: []`) — every entity that isn't of this shape keeps its exact pre-fix behavior.
- `evaluateEntityCoverage()` (`lib/generation/qa/text.ts`) reuses the existing `containsNormalized()` Markdown-insensitive matcher (unchanged) against `primary` first, then each alias, returning `"full"` (primary present), `"partial"` (only an alias present), or `"none"` (neither) — exactly two literal substring checks per alias, nothing broader.
- `checkEntities()` (`lib/generation/qa/checks/entities.ts`) now classifies each assigned entity via `evaluateEntityCoverage()`: **PASS** when every entity is `full`; **FAIL** only when every entity is `none` (a genuinely, wholly missing set — unchanged from before); **WARN** for any mix, with the finding text now naming which entities are missing entirely versus present only via alias, rather than conflating the two as before.
- Deterministic regression tests added (`lib/generation/qa/text.verify.ts`, run via `npx tsx lib/generation/qa/text.verify.ts`) covering the 5 required cases: exact full entity, primary-with-untriggered-alias, alias-only, genuinely absent, and Markdown formatting inside the body around the primary term (reusing `containsNormalized` unmodified, unaffected by this change).

**Verified against real, live data**, not just the regression suite: re-running QA against project `ce718b4d-25e1-40f6-9af5-9716c7ce1aa0` after the fix reduced the project's total blocking findings from 10 to 5 — several sections whose entity was in fact present, just under an alias, moved from an undifferentiated "missing" WARN to a finding that correctly names the alias it matched (e.g. `"1/3 assigned entities need attention: 1 present only via alias, not the primary term (Bolognese sauce (ragu alla bolognese) — matched \"ragu alla bolognese\")"`), while sections with a genuinely absent entity (no primary, no alias, anywhere in the body) are unchanged.

This does not alter QD3 (still exactly one deterministic method for `entities`, no LLM introduced) or the category's severity model (§4) — FAIL still requires total absence, WARN is still the default for a partial/mixed result, PASS still requires full coverage. It only changes what counts as "present" for an entity that carries its own author-supplied alias.

## QD10: entity coverage rule — confirmed implementation finding that literal contiguous-phrase matching is too strict for multi-word entities (QA-10, 2026-08-20 — superseded by the LOCKED, IMPLEMENTED, LIVE-VERIFIED rule below, QA-13/QA-14/QA-15/QA-16)

Found by auditing a real, live FAIL — not hypothesized. Project `ce718b4d-25e1-40f6-9af5-9716c7ce1aa0`, section **"Choosing the Right Pasta for Bolognese"**, `content_versions.id = a67e771c-c23f-42e7-a86c-0ccaceb02e5b`. `checkEntities()` reported: *"None of this section's assigned entities appear in its body: Spaghetti pasta, Bolognese sauce (ragu alla bolognese), Italian cuisine, Pasta cooking techniques."* — reproduced identically across all 3 stored `qa_reports` for this project, confirming this is not a one-off fluke of a single run.

**The body, read directly, plainly engages with all four concepts:**

> "When most Americans think of bolognese, spaghetti is the first pasta that comes to mind... other pasta shapes also pair beautifully with bolognese. Tagliatelle... is often cited as a more traditional Italian pairing for a rich meat ragu... flat or ridged shapes tend to hold a hearty sauce better... cook it to al dente..."

**Root cause, traced precisely:** `evaluateEntityCoverage()` (`lib/generation/qa/text.ts`) calls `containsNormalized(body, primary)` — a single, literal, *contiguous-substring* check of the entire multi-word entity phrase. English prose routinely splits a compound noun phrase across a clause (*"spaghetti is the **first pasta**"* — never the contiguous string "spaghetti pasta"), uses a different word order, or drops one generic word from a two-word phrase (*"Italian **pairing**"*, not "Italian cuisine"; *"cook it to al dente"*, not "pasta cooking techniques"). None of this is a Markdown-formatting issue (already fixed) or a missing-alias issue (already fixed) — it is a **word-order/paraphrase** issue the two prior fixes do not address, because both prior fixes still ultimately delegate to the same single contiguous-phrase `containsNormalized()` call.

**This is a genuine over-strict false FAIL, not a genuine content gap** — verified by manual inspection of the real body against each of the four entities:

| Entity | Body evidence | Verdict under today's rule | Verdict on the merits |
|---|---|---|---|
| Spaghetti pasta | "spaghetti is the first **pasta**..." (both words present, not adjacent) | none (FAIL) | substantively covered |
| Bolognese sauce (ragu alla bolognese) | "pair... with **bolognese**", "a rich meat **ragu**" (primary word + alias word present, neither full phrase) | none (FAIL) | substantively covered, partially |
| Italian cuisine | "a more traditional **Italian** pairing" (topic word present, "cuisine" absent) | none (FAIL) | substantively covered, partially |
| Pasta cooking techniques | "**pasta** shapes...", "**cook** it to al dente" (pasta present; "cooking"/"techniques" absent, "cook" is a different inflection) | none (FAIL) | weakly covered |

### The first-principles question: what should an entity requirement mean?

Evaluated against this task's own four options:

- **(A) Exact phrase presence** — today's actual rule (a full-string `containsNormalized` match, regardless of what "normalized" strips). Proven above to produce a false FAIL on ordinary, well-written prose. **Rejected — this is the bug.**
- **(B) Normalized primary/alias presence** — already implemented (Markdown-syntax normalization, LEAVES-01's primary/alias split). Necessary, but insufficient on its own: (B) is still option (A) applied twice (once to the primary, once per alias) — it does not address word-order/paraphrase at all, which is exactly what this audit's false FAIL turns on.
- **(C) Deterministic concept/phrase coverage using a controlled representation** — **recommended.** Decompose the entity's own primary (and each alias) into its *own* significant-word set using the exact same `significantWords()` primitive `checkTopics()` already uses for the same purpose (title-term coverage) — reusing an established, trusted primitive rather than inventing a new one. Score coverage as the fraction of that word set found anywhere in the body (via the existing `containsNormalized()`, word-by-word — Markdown-insensitive, case-insensitive, unchanged matching discipline), then classify using **the exact same ratio thresholds `checkTopics()` already established and this project already trusts**: `ratio === 0` → `none`; `ratio < 0.5` → `partial`; `ratio >= 0.5` → `full`. A full literal contiguous-phrase match trivially implies 100% word coverage, so every entity that legitimately passes today keeps passing — this is a relaxation, not a replacement, of the existing rule.
- **(D) Something else (embeddings/LLM semantic judgment)** — explicitly not chosen. Nothing in this audit demonstrates a *semantic* gap (the concepts are covered using recognizable, literal words — just not as one contiguous phrase); reaching for embeddings/an LLM here would trade a deterministic, reproducible, git-diffable check for a nondeterministic one to solve a problem that a small, inspectable, deterministic fix already solves. Matches this project's own standing discipline (D5/D6/QD3) of not reaching for AI where a deterministic rule is available.

### Recommended rule (proposed at the time this analysis was written — since locked as QD10 and implemented; see the LOCKED/IMPLEMENTED sections below for the final rule and live-verification evidence)

Reusing existing primitives only — `significantWords()` (`lib/generation/qa/text.ts`, already used by `checkTopics()`), `containsNormalized()` (already used by both `checkTopics()` and `checkEntities()`), and `parseEntity()`'s existing primary/alias split (LEAVES-01, unchanged):

1. For the entity's `primary` string, compute `significantWords(primary)` (stopword-filtered, length ≥ 4, deduplicated — the exact existing primitive, no new one). If empty (a primary too short/generic to tokenize — a real but rare edge case), fall back to today's exact literal `containsNormalized(body, primary)` check, preserving current behavior for that shape rather than vacuously auto-passing.
2. Coverage ratio = (count of those words individually found in the body via `containsNormalized`) / (total word count). Classify: `ratio === 0` → `none`; `0 < ratio < 0.5` → `partial`; `ratio >= 0.5` → `full` — literally `checkTopics()`'s own three-way split, applied to a per-entity word set instead of a per-title word set.
3. Repeat the same computation for each alias (LEAVES-01's existing `aliases[]`); an entity's overall coverage is the *best* of primary-coverage and any alias-coverage (unchanged "primary or alias, whichever is stronger" precedent from LEAVES-01).
4. Section-level rollup (`checkEntities()`'s own FAIL/WARN/PASS logic) is **unchanged in shape** — FAIL only when every entity is `none`; WARN for any mix of `none`/`partial`; PASS only when every entity is `full`. Only the per-entity `full`/`partial`/`none` *classification* changes; the rollup formula does not.

Applied to the real audit data: Spaghetti pasta → `full` (2/2 words); Bolognese sauce (ragu alla bolognese) → primary 1/2 = `partial`, alias "ragu alla bolognese" 2/3 ≈ 0.67 = `full` → entity `full` (best-of); Italian cuisine → 1/2 = `partial` (exactly the 0.5 boundary reads as `full` under `checkTopics()`'s own `ratio >= 0.5` cutoff — reused verbatim, not redefined); Pasta cooking techniques → 1/3 ≈ 0.33 = `partial`. **Section rollup: WARN** (a real, visible, honestly-described partial-coverage signal), not the current false FAIL — while a section that genuinely never mentions any of its assigned concepts (0 words of any entity found anywhere) still correctly rolls up to FAIL, unchanged.

### Why this does not regress the two already-fixed cases (this task's own requirement 4)

- **Markdown-normalization fix (unchanged):** every comparison in the new rule still routes through `containsNormalized()` — Markdown-syntax stripping is untouched, applies identically to whole-phrase and per-word matching alike.
- **Parenthetical-alias fix (unchanged):** `parseEntity()`'s primary/alias split is reused exactly as-is; the new rule only changes *how* each of primary/alias is matched (word-set ratio instead of one literal substring), not *whether* aliases are considered at all.
- **Genuine misses still fail:** an entity truly absent (0 of its own words anywhere in the body) still scores `none` under the new rule, identical to today — this was directly verified against the same project's other real FAIL cases (Phase 4.6 plan's own "Step 5 section... unaffected by this fix" precedent from the Markdown-normalization fix) is expected to hold the same way here, and must be re-verified against real data at implementation time before this is locked.

### Resistance to false positives (this task's own explicit requirement)

A single shared generic word is not enough to flip a multi-word entity to `full` — the `ratio >= 0.5` cutoff requires at least half of the entity's own defining words, and single-word entities (the common case for simpler Blueprints) are completely unaffected (ratio can only be 0 or 1 for a one-word set, identical to today's exact-match behavior — zero regression risk for that shape). A weak, single-word match on an otherwise-unrelated multi-word entity lands at `partial` (visible WARN), never silently `full`/PASS.

**Status at time of original QA-10 analysis: proposal only, not locked.** Superseded first by the QA-11 audit (which found the original ratio-based rule, `ratio >= 0.5` → `full`, unsafe as worded and recommended a stricter refinement) and then by QA-13's review, which **locked** that refinement as QD10. See below for the audit evidence and the final locked rule text.

### False-positive risk: confirmed, not hypothetical

**Cases 6 and 7 are real, confirmed false positives under the original QA-10 ratio (`ratio >= 0.5` → `full`).** Case 6 uses a real entity ("Italian cuisine") and a real body from the same project (borrowed from a sibling section for stress-testing, matching this task's own example): the body says "Italian pairing," never engaging with "cuisine" as a concept at all, yet the 0.5-ratio rule (1 of 2 significant words present) would classify this as `full` — a section that never discusses the assigned concept would silently PASS. Case 7 (synthetic, deliberately constructed per this task's own "two generic tokens" instruction) shows the same failure mode more sharply: an entity's two *generic* words ("fresh," "garnish") being present is enough to cross the 0.5 bar even though the one *specific*, defining word ("basil") is completely absent. **The original QA-10 Option C wording is confirmed unsafe as written and should not be locked.**

**Root cause of the false positives:** a flat word-presence ratio treats every significant word as equally diagnostic. It is not — in a short (2–3 word) noun phrase, a single generic/category word (cuisine, sauce, garnish, techniques) can single-handedly cross a 50% bar without the phrase's actual distinguishing term ever being mentioned. No purely positional heuristic (require the first word; require the last word) reliably separates "generic" from "specific" either — this project's own real entities put the specific term first in some cases ("Italian cuisine" — Italian is specific) and effectively synonymous-either-way in others ("Bolognese sauce" — Bolognese is specific, sauce is generic but the reverse convention also occurs in casual prose). A within-document IDF-style weighting (down-weighting words that recur across a Blueprint's own entity list, the same technique already trusted in this codebase for `lib/generation/content/evidence.ts`) was considered but rejected for this specific fix: a typical Blueprint's entity list (this project has ~13 unique entities) is too small for word-recurrence to reliably distinguish genuinely generic English words (cuisine, garnish, techniques) that just don't happen to repeat within one project's own small entity vocabulary.

### LOCKED rule (QD10, 2026-08-20, QA-13): require ALL significant words present for `full`

Same mechanism as Option C (reuse `significantWords()`/`containsNormalized()`, word-set membership, order-independent — this is what fixes the real false-negative bug, case 4/5), but a stricter classification: **`full` requires every one of the entity's own significant words to be found somewhere in the body (ratio === 1.0, not ≥ 0.5); any non-empty subset scores `partial`; zero scores `none`.** Because this only ever *removes* the contiguity/adjacency/order requirement from today's literal-phrase check while keeping full lexical coverage mandatory, it is a **pure superset relaxation** of today's rule for word-*order* (can only turn a false `none` into a correct `full`/`partial`, never the reverse) while adding **no new false-positive surface area** beyond "the same words, in a different order" — the strongest deterministic signal available without semantic understanding.

**Re-run against all 12 cases:** fixes the real audited bug (case 4: none → partial, an honest WARN instead of a false FAIL); fixes both confirmed false positives (case 6: full → partial; case 7: full → partial, no longer silently PASS-eq); preserves every already-correct case unchanged (1, 2, 8, 9, 10, 12) or improves it (5: none → full, the word-order case, correctly). **One acknowledged, deliberate trade-off:** case 11 (a real-shaped 4-word entity missing exactly one minor/generic word, "whole") drops from what the original ratio rule scored as `full` to `partial` under the stricter rule — a legitimately well-covered long entity is under-credited to WARN rather than PASS. This is judged an acceptable, conservative trade-off, not a flaw to fix immediately: a WARN is visible and reviewable in seconds; a false PASS (cases 6/7's failure mode) is never reviewed by anyone, because nothing prompts a human to look again. Matches this document's own established asymmetric-severity philosophy (§4 — "WARN is the default... for anything short of an unambiguous violation," applied to `factual`) of preferring a visible, non-blocking WARN over a silent false confidence signal when a rule is genuinely uncertain.

**No purely deterministic rule perfectly separates "missing an unimportant word" (case 11, should stay `full`) from "missing the one important word" (case 7, must not be `full`) without additional signal about which word actually carries the meaning** — stated plainly as a real, acknowledged limitation, not oversold as a complete fix. Embeddings/LLM semantic judgment would resolve this ambiguity but were explicitly excluded from this audit's scope per instruction; the refined all-words-required rule is the safer, still fully deterministic middle ground given that constraint.

**Confirmed no regression to either already-shipped fix:** Markdown-syntax normalization is untouched (every comparison still routes through `containsNormalized()`, case 9 unaffected); the parenthetical-alias mechanism (`parseEntity()`) is reused exactly as-is, only the per-string scoring changed (case 2/3 unaffected — case 3 in fact now resolves via the primary's own word-set without even needing the alias fallback, a side effect of order-independence, not a change to alias logic itself).

### Rationale (why this rule, locked as written)

- **Deterministic, reproducible, inspectable** — every classification is a plain word-membership count over two already-existing, already-trusted primitives (`significantWords()`, `containsNormalized()`); no external corpus, no model call, no randomness. Anyone can recompute a finding's classification by hand from the entity string and the body text alone.
- **No embeddings, no LLM semantic judgment** — considered and explicitly rejected for this fix (this task's own constraint, restated from QA-11): the false positives found in cases 6/7 are a *word-selection* problem (which words count as evidence), not a *semantic-understanding* problem language models would be needed to solve.
- **A single generic token cannot produce a false PASS** — the previous `ratio >= 0.5` rule let one generic word ("cuisine," "garnish," "techniques" being *absent* while a co-occurring generic word was present) cross the bar for short entities. Requiring *all* significant words removes this failure mode entirely: a `full` classification now requires the same lexical coverage a literal phrase match would have required, just without demanding contiguity/order.
- **Existing genuine misses remain FAIL** — an entity with zero of its own words anywhere in the body still scores `none` under this rule, identical to today; this is a pure relaxation of the *order/contiguity* requirement, never a relaxation of *lexical coverage*.
- **Existing fixes are preserved exactly** — Markdown-insensitive matching (`containsNormalized()`) and the parenthetical-alias split (`parseEntity()`, LEAVES-01) are both reused completely unmodified; this rule changes only how many of a representation's own words must be found, not how "found" itself is determined or how aliases are considered.

### Known conservative trade-off (accepted, stated explicitly — not hidden)

A section that substantively covers an entity's concept but omits exactly one minor/generic word (case 11's audited example: "San Marzano canned whole tomatoes," missing only "whole") receives **WARN, not PASS**, under this rule. This is an intentional, accepted trade-off for V1, not an oversight: **a silent false PASS is judged more damaging to QA trust than a conservative WARN a human can dismiss in one glance.** A false PASS is never reviewed by anyone — nothing prompts a second look — while a WARN is visible, expected, and cheap to confirm. This mirrors this document's own pre-existing asymmetric-severity philosophy (§4, the `factual` category's "WARN is the default... for anything short of an unambiguous violation" reasoning) applied to a new category. No purely deterministic rule can perfectly distinguish "missing an unimportant word" from "missing the one important word" without additional signal about which word carries the meaning — embeddings/LLM judgment could resolve this ambiguity but are explicitly out of scope, so this trade-off is accepted rather than engineered away.

## Partial QA (QD9, locked 2026-08-20, LEAVES-04)

**Status: locked architecture. Not implemented — no migration, no code, no Anthropic calls made producing or locking this section**, matching this document's own planning-only constraint. Raised as a proposal during LEAVES-03 (real cost/UX gap: a user who only cares whether a manual edit broke `entities`/`links` today has to pay for a full run — both LLM calls, all 7 deterministic checks — to find out); reviewed and **locked, without amendment to this section's own architecture, as QD9** during LEAVES-04, alongside the required QD4 cost-control amendment above. A distinct concept from ED12's "Export without QA" full bypass (see the dedicated comparison subsection below), and distinct from a stale/FAIL report (a partial report is a **real, honest, smaller-scope** result, not a degraded or overridden one).

**A. Selection and persistence.** A QA run accepts an optional `selectedCategories: QaCategory[]` (server-validated non-empty — a zero-category "run" is rejected server-side, matching this project's own "server re-checks independently" discipline; the UI should never let a user reach that state either, but the guarantee is server-side, not just a disabled button). Omitting the parameter (the existing, unchanged call shape) means "all 9" — full QA remains the literal default, not a special case of partial QA. Every QA run — full or partial — still produces exactly one new, immutable `qa_reports` row (QD5, unchanged); a later run, full or partial, always creates a *new* report, never edits an old one. No existing report is ever mutated to add/remove/hide a finding — this proposal changes nothing about QD5's immutability guarantee or the "no UPDATE/DELETE policy on `qa_reports`/`qa_findings`" RLS enforcement (§12, unchanged) that makes hiding a FAIL structurally impossible today.

**B. What "evaluated" vs "skipped" means, precisely.** Only the selected categories are actually computed: for the 7 deterministic categories, only the selected check functions run at all (`checkTopics`/`checkEntities`/etc. are already independent, side-effect-free functions per leaf — trivially made conditional, QD3's "no blending" design already implies no inter-category dependency); for `intent`/`factual`, the corresponding LLM call is made only if that category is selected, and **not made at all** if neither is selected (this is where the real cost saving lives — requirement F). A skipped category produces **zero `qa_findings` rows** — never a synthetic "N/A" finding, and never silently re-using an old report's findings for that category. This is deliberately not "run everything, then hide the unselected ones from the UI" — that would still spend the AI cost this proposal exists to save, and would leave misleading `qa_findings` rows in the database for a category the user asked to skip.

**C. The real reason "evaluated"/"skipped" cannot be derived after the fact — a concrete precedent already observed in this project.** A category having zero `qa_findings` rows is **not** a reliable signal that it was skipped: this project's own QA backend already produced a real, correctly-designed case where an *evaluated* category (`factual`) legitimately made zero LLM calls and produced zero findings, because there was nothing to batch (recorded in `docs/PROJECT-TAKEOVER.md`'s Phase 4.6 section — the thin-project QA run against `64f3a6aa-...`). If "skipped" were inferred from "no findings exist for this category," that real, correct zero-finding case would be indistinguishable from a genuinely skipped category — exactly the ambiguity requirement H warns against. **This is why evaluated/skipped category sets must be explicitly persisted, not derived.**

**D. Schema gap (requirement E) — the existing schema cannot represent this today.** Reviewed directly against `20260817000010_qa.sql`: `qa_reports` has no column recording which of the 9 categories a given run actually covered — it was designed, correctly for its own time, around QD5's original "a report is always a complete 9-category run" invariant, which this proposal is the first thing to actually relax. **Smallest proposed additive change (no migration created by this document):**

```
alter table qa_reports
  add column evaluated_categories qa_category[] not null default array[
    'intent','topics','entities','structure','links','brand','factual','style','forbidden_chars'
  ]::qa_category[],
  add column skipped_categories qa_category[] not null default '{}'::qa_category[];
```

Both arrays are populated once, at report-creation time, from the actual selection the run was given — never recomputed later. The `default` shown is a backfill convenience for every pre-existing `qa_reports` row (all of which really were full 9-category runs under the old, unmodified behavior) — new rows always pass explicit values, never rely on the default. **Both arrays are stored, not just one with the other derived as "the complement of the frozen 9,"** per the task's own explicit requirement — deliberately future-proofed: if the frozen category set itself ever changes (a 10th category added, one retired), an old report's `skipped_categories` stays a permanently accurate, self-describing record of what it actually skipped *at the time*, without needing to know what "the full set" was back then to compute a complement. `qa_findings` itself needs no schema change — QD1's existing `content_version_id` anchor and the category/method/status/note/quote shape are unaffected; a skipped category simply contributes no rows.

**E. Rollup/severity — unchanged mechanism, reframed meaning.** `overall_status`'s existing rollup (FAIL if any finding fail, else WARN if any warn, else PASS, §4) is computed only over findings that exist — which, for a partial report, means only over the evaluated categories, automatically (skipped categories contribute zero findings, so they mathematically cannot flip the rollup either direction). The computation itself needs no change. **What must change is presentation, not computation** (the QA-UI plan's job, see the companion update there): a partial report's PASS must never be displayed as an unqualified "PASS" the way a full report's is — it must always carry its own "N/9 categories evaluated" framing, everywhere it's shown, matching requirement H's "must never look like a full QA pass."

**F. Cost/performance (requirement F) — a real, demonstrable saving, not just fewer displayed rows.** QD4's "exactly 2 LLM calls per run, flat regardless of document length" becomes, under this proposal, "0, 1, or 2 LLM calls depending on selection" — a user who only selects deterministic categories (`entities`, `links`, `brand`, etc.) triggers **zero** Anthropic calls, the cheapest and fastest possible QA run this architecture can produce, useful for exactly the "did my manual edit break something mechanical" case that motivated this proposal. QD4's own flat-cost property is preserved *within* whatever's selected — `factual`, if selected, is still one batched call across every evaluated leaf, never N calls.

**G. Relationship to ED12 ("Export without QA") — requirement D, answered explicitly.** These are categorically different concepts, not two flavors of the same thing:

| | ED12 bypass | QD9 partial QA |
|---|---|---|
| When the choice is made | At **export** time, after a report already exists (or doesn't) and is blocking | At **QA-run** time, before any report exists — a property of the report itself |
| What it represents | The human explicitly **overrides** the system's QA judgment (or its absence) | The system's QA judgment **is followed** — just computed over a smaller, honestly-labeled scope |
| Resulting trust signal | **Unverified** — no machine-checked evidence backs the export, regardless of whether a report existed | **Partially verified** — real, machine-checked evidence exists for the evaluated categories; the rest is honestly marked unchecked |
| `qa_bypassed` on the resulting export | `true`, always | `false` — a partial-QA export goes through the *normal* Export gate/action, not the bypass path (see the companion Export-plan update, ED13 proposal) |
| Can the two combine? | Yes, indirectly: a partial report that itself FAILs or goes stale still only becomes exportable via ED12's bypass, exactly like a full report in the same state — QD9 does not soften ED12's own bar in any way. | — |

**H. Safety (requirement H) — restated as the governing constraint on everything above.** A partial report must never render as, be computed as, or be mistaken for a full QA pass, anywhere: not in `overall_status`'s own meaning (§E), not in the QA tab (companion UI-plan update), not in an exported file's metadata (companion Export-plan update). A skipped category is never silently treated as PASS — it has no finding, no status, and is rendered as an explicit "Not evaluated" state distinct from all three of PASS/WARN/FAIL, every place a category is shown.

## Key risks, ranked

1. **The `factual` category is the sharpest correctness-and-trust risk in this entire design**, for a reason distinct from every prior phase's grounding risk: earlier stages worried about the *writer* fabricating; this is the first stage where a fabricating *reviewer* could produce a false FAIL that blocks Export, or a false PASS that gives false confidence. §4/§7/§13's mitigations (narrow FAIL bar, mandatory quoted excerpts, evidence parity with what the writer actually saw) reduce but do not eliminate this — the single most important thing to watch once real QA runs happen, mirroring how Phase 4.5 flagged its own §0/§7 grounding risk as "the sharpest correctness risk," which is exactly the same shape of problem one layer later in the pipeline.
2. **QD1 (`qa_findings.content_version_id`) is a required schema change, not optional polish** — without it, the Content Editor / QA tab UI has no way to show "this finding is about section X," which is table-stakes for the QA tab as designed (a category list a human can act on). Should land before any QA UI is built, same urgency class as CD3 was for Content's parallel-section generation.
3. **QD6 (staleness blocking Export) is a genuine design decision this document is making, not merely restating Design V1** — the frozen design doc predates QA being reachable and doesn't explicitly address "what if the content changed after the last green QA run." Getting this wrong (treating a stale PASS as a real PASS) would let a project export un-reviewed content while showing a reassuring green banner — worse than having no QA result at all.
4. **QD2 (re-running deterministic guards on manually-edited content) is a real, previously-invisible gap**, not a hypothetical — every manually-edited section today has genuinely never been checked for em dashes, forbidden phrases, or link whitelist violations by anything. This isn't a QA nice-to-have; it's closing a hole that exists in the shipped Phase 4.5 code right now.
5. **False-positive fatigue on `intent`/`factual` is a real usability risk if the LLM's judgment calls prove noisy in practice** — no per-finding override exists by design (QD5), so a high false-positive rate would be felt as "QA is annoying to satisfy," not silently absorbed. Worth watching once real QA runs happen; the fix, if needed, is narrowing the FAIL bar or quote requirements further (§7), not adding an override button.
6. **QD9 is a real trust-signal risk if presentation drifts from the data model** — the entire safety case for Partial QA rests on a partial PASS never being visually or textually indistinguishable from a full PASS, everywhere it's shown (QA tab, Export tab, exported file metadata). If any one of those three surfaces is implemented without the "N/9 evaluated" qualifier, the whole point of storing `evaluated_categories`/`skipped_categories` explicitly is undermined at the last, most user-visible step. Worth the same "check every surface, not just the database" scrutiny already flagged for ED12's `qa_bypassed`.
7. **QD8's "one `generation_runs` row per QA run, two calls summed into it" is a minor but real telemetry-fidelity tradeoff** — a full per-call cost/token breakdown lives only in `metadata` (jsonb), not first-class columns, unlike every other stage's exactly-one-call-per-row telemetry. Acceptable because QA is the first stage with a legitimate multi-call-per-Generation shape, but worth naming so it isn't mistaken for an oversight later.

## Explicitly out of scope (Question 25)

- **Per-finding dismiss/resolve/override UI** (§6, QD5) — rejected, not deferred; the correction path is fix-then-re-run-whole-report.
- **Per-category or per-finding re-run** (§6, QD5) — only whole-report re-run exists.
- **A blended/weighted QA score** — category-level PASS/WARN/FAIL only, unchanged from Design V1 rule #6.
- **LLM-based checks for the 7 deterministic categories** — `topics`/`entities`/`structure`/`links`/`brand`/`style`/`forbidden_chars` stay fully deterministic; do not "upgrade" any of them to an LLM judgment call later without a demonstrated deterministic-approach failure, same anti-scope-creep discipline as every prior phase.
- **Deterministic fact-verification of arbitrary prose claims** — still a genuinely open NLP problem (Phase 4.5 §7's conclusion, unchanged); `factual`'s LLM check + mandatory quotes (§13) is the honest, buildable substitute, not a claim to have solved it.
- **Automatic QA triggered by every Content edit/regenerate** (§9) — on-demand only, no auto-QA-on-save.
- **Export implementation itself** — Phase 4.7's job; this document only defines the gating *signal* Export must consume (§5, QD6), not Export's own build.
- **Cross-project QA trend dashboards, historical reporting, or a QA cost dashboard** — telemetry is captured (QD8), not surfaced anywhere beyond the QA tab itself, matching D7/D8's original "capture only" scope limitation from Phase 4.2.
- **A new, fifth provenance category** — QA findings stay classified under the existing four-value model (§11), no new category invented.
- **Any `engine.ts` change** — the third stage in a row to prove the three-phase lifecycle needs zero modification; if implementation finds it actually does need one, that's a signal worth stopping and re-examining, not a quiet workaround.
- **A `qa_reports` "current version" head-pointer table** — unnecessary; QA reports are a diagnostic history queried by recency, not a versioned artifact with its own current-pointer concept (§10).
