# Phase 4.3 — Strategy Brief Generation: Implementation Plan

Status: planning only. No code, migrations, or API calls were made producing this document.
Provider: Anthropic. Model: `claude-sonnet-4-6`, read from `ANTHROPIC_MODEL` (currently blank in `.env.local`, confirmed at inspection time — must be set before implementation). API key stays in `.env.local` only; never printed, logged, committed, or included in diagnostic output at any point in this phase, including during implementation/debugging.

## Locked decisions (final, this pass)

The three previously-open decisions from §0.1, §0.8, and §8 are now resolved and locked. Nothing below is subject to further relitigation absent a demonstrated need.

| # | Decision | Status |
|---|---|---|
| L1 | **Request changes.** An approved Brief can be moved to `needs_revision` via "Request changes." This transition alone never starts generation. The user must explicitly edit the brief's inputs/instructions, then trigger a separate "Regenerate" action. The existing approved version is never mutated — it remains immutable and retrievable. | **LOCKED** |
| L2 | **Generation API split.** The D1 three-phase persistence lifecycle is approved exactly as proposed in §0.1: `recordProviderCompleted()` → `recordArtifactPersisted()` → `completeGeneration()`. This is now the required implementation shape for `lib/generation/engine.ts`, not a proposal pending sign-off. | **LOCKED** |
| L3 | **Regeneration after approval.** Regeneration is allowed on an already-approved Brief, with no gating beyond L1's "must go through Request changes first" flow. Every regeneration — approved-source or draft-source — always creates a new `brief_versions` row starting at `status='draft'`, requiring its own separate approval. The prior approved version is never mutated and remains permanently immutable. | **LOCKED** |

## 0. Architecture challenges surfaced by this inspection

These are real gaps found by re-reading the shipped Phase 4.2 code and current schema, not generic commentary. Each is a required decision or change before Brief generation can be built correctly.

1. **`completeGeneration()` doesn't actually support D1's three-phase pattern yet.** The Phase 4.2 skeleton collapses `provider_completed_at`/`artifact_persisted_at`/`completed_at` into one atomic update, because nothing was writing a real artifact between "got provider response" and "done." Brief generation is the first stage that genuinely needs the split: receive Claude's response → durably store it (`provider_completed`) → parse and insert `brief_versions`/`brief_topics`/`brief_internal_links`/flip the head pointer (`artifact_persisted` → `completed`), where the second step can fail independently of the first having already succeeded. This requires changing `lib/generation/engine.ts`'s public API (breaking change to `completeGeneration`'s contract — safe, since no stage currently calls it in production). Proposed shape:
   - `recordProviderCompleted(generationRunId, { outputRef, provider, model, providerRequestId, inputTokens, outputTokens, totalTokens, estimatedCostUsd, finishReason })` — sets `status='provider_completed'`, `provider_completed_at=now()`. Called immediately after the Storage write, before any parsing/DB insert is attempted.
   - `recordArtifactPersisted(generationRunId)` — sets `status='artifact_persisted'`, `artifact_persisted_at=now()`. Called immediately after the `brief_versions` row (+ children + head-flip) is fully inserted.
   - `completeGeneration(generationRunId)` — shrinks to the final mechanical flip: `status='completed'`, `completed_at=now()`, `duration_ms` computed from `started_at`. No longer accepts telemetry (already captured in step 1).
   - `recoverGeneration`'s existing `artifact_persisted → completed` branch should become a thin wrapper around the same logic `completeGeneration` uses, so there is one implementation of that transition, not two.
   **Approved — see L2 in "Locked decisions" above.** This is now the required implementation shape; it changes already-shipped code's public signature, which is accepted since no stage currently calls it in production.

2. **`brief_topics` and `brief_versions.entities_concepts`/`questions` look redundant but aren't — they encode different provenance.** Per the locked provenance rules (Research finding vs AI recommendation), `brief_topics` should hold the "Topics, entities & questions to cover" chip list Design V1 marks as **Research finding** — meaning it must be derived deterministically from `research_sources` by app code, not generated by the LLM call at all. The `entities_concepts`/`questions` JSONB columns on `brief_versions` are Claude's own synthesis (**AI recommendation**, editable). Building both from a single Claude call would silently mislabel research data as an AI opinion. Plan: the Brief stage does two separate things — (a) deterministic extraction of `brief_topics` rows from `research_sources` (no LLM), (b) one Claude call producing everything else.

3. **`brief_internal_links` will legitimately be empty for every real project today.** Nothing in the codebase populates `internal_link_candidates`, and `website_urls` ingestion is still simulated (no real sitemap/Screaming Frog parser exists). Per the "never fabricate" rule, Claude must not invent plausible-looking URLs when given no real website data. Plan: pass whatever `website_urls`/`internal_link_candidates` rows exist (possibly zero) into the prompt, instruct the model to return an empty array when there is nothing real to link to, and validate that any returned `target_url` corresponds to a row actually supplied in context (reject/strip anything that isn't).

4. **No multi-row transaction primitive available at the client layer.** Persisting one Brief version means inserting `brief_versions` + `brief_topics` + `brief_internal_links` + updating `content_briefs.current_version_id`, atomically ideally. The Supabase JS client (server-side, `authenticated` role) has no ad-hoc multi-statement transaction. Plan for V1: insert `brief_versions` first (the anchor row, self-sufficient), then children, then flip the head pointer last. If children fail partway, the version row exists but isn't yet "current" — this is a safe, recoverable intermediate state that maps cleanly onto "not yet `artifact_persisted`." A real DB-transaction via an RPC function would be more robust but is not justified for a first implementation — noted as a future hardening option, not built now.

5. **RLS is fully unpoliced on all four Brief tables.** `content_briefs`, `brief_versions`, `brief_topics`, `brief_internal_links` have RLS enabled with zero policies — the same "fully locked" trap that caused real bugs twice already in this project (`projects`, `generation_runs`). This blocks Phase 4.3 entirely until fixed. See §12.

6. **Two state machines need to be touched, and the wiring isn't specified anywhere yet.** `projects.generation_state` (fine-grained pipeline enum, Phase 4.1) and `projects.status` (coarser Dashboard-facing enum, Phase 0/3) are separate systems. Nothing today advances `projects.status` past `ready_for_brief`. Approving a Brief needs to move `generation_state` forward (via `transitionGenerationState`, already built) **and** `projects.status` forward (e.g. to `brief_generated` on first successful generation, `brief_approved` on approval) so the Dashboard badge stays accurate. This must be an explicit part of the Brief stage/approval action, not assumed to happen automatically.

7. **Naming inconsistency: `brief_versions.model_id` vs `generation_runs.model`.** The Phase 4.2 rename (`model_id` → `model`) only touched `generation_runs`. `brief_versions.model_id` was never renamed. Flagging for awareness; not proposing a migration to rename it in this phase (out of scope, cosmetic, no functional risk) unless you want it folded into the RLS migration for consistency.

8. **"Request changes" behavior — resolved, see L1.** Approved → `needs_revision` (not `changes_requested` — align the status value with this name at implementation time). The transition alone does not start generation; the user must edit the Brief's inputs/instructions and separately trigger Regenerate. Still unbuilt as of this planning pass (see §11), but no longer an open design question.

## 2. Exact Strategy Brief output schema

Two distinct outputs, matching the provenance split in §0.2:

**A. Claude-generated (one structured tool-use call), maps 1:1 to `brief_versions` columns:**
`search_intent_label`, `search_intent_confidence` (0–1), `search_intent_rationale`, `target_audience`, `content_objective`, `secondary_topics` (string[]), `serp_interpretation`, `common_competitor_expectations`, `unique_value`, `title`, `h1`, `meta_description`, `entities_concepts` (string[]), `questions` (string[]), `evidence_requirements` (string[]), `things_to_avoid` (string[]), `business_brand_alignment`, `research_limitations`.

Plus `brief_internal_links` candidates (anchor_text/target_url pairs, or empty array) as a distinct output block — AI-recommended, per §0.3.

**B. Deterministic, app-derived (no LLM):**
`brief_topics` rows — one per distinct topic/entity/question surfaced directly from `research_sources` rows for the current package, tagged with `label`. Built in application code from the already-parsed research data, independent of the Claude call succeeding or failing in any particular way (though it still only runs after a successful call, since a Brief without AI synthesis is incomplete).

## 3. Artifact/version storage

Sequence, executed as the `artifact_persisted` phase (see §0.1/§0.4):

1. `content_briefs` head row: fetch if exists for `project_id`, else insert (first generation for the project).
2. Insert `brief_versions` row: `version = max(existing)+1`, `status='draft'`, `project_id`, `generation_run_id`, `model_id` (Claude's reported model), `prompt_version` (e.g. `"brief@1"`), all schema fields from §2A, `created_by`.
3. Insert `brief_topics` rows (from §2B).
4. Insert `brief_internal_links` rows (from §2A, possibly zero rows).
5. Update `content_briefs.current_version_id` to the new version's id — this is the head-flip, done last, and is the actual "artifact_persisted" boundary in practice: if steps 2–4 succeeded but this update hasn't run, the version exists but isn't current, which is a safe partial state.

No existing version is ever mutated or deleted — matches the locked versioning model used elsewhere.

## 4. Prompt structure

New file: `lib/ai/prompts/brief/v1.ts`, exporting:
- `PROMPT_VERSION = "brief@1"` (file-based, per D4 — never DB-stored/editable).
- System prompt: role framing, brand/tone instructions if a brand profile is present, explicit "no em dash" instruction (defense in depth — the deterministic check in §7 is the actual enforcement).
- Injected context blocks, each clearly delimited and explicitly labeled as **reference data, not instructions** (first real implementation of the prompt-injection mitigation flagged in the original Phase 4 design doc — research content and `projects.instructions` are both user/externally-sourced and must be fenced off from being interpreted as directives to the model).
- Output contract: Anthropic tool-use with a forced `tool_choice`, schema matching §2A exactly.

Today's actual `research_sources` payload (per the real Markdown parser) is lightweight metadata only — no raw competitor page bodies are extracted or stored — so the context-budget risk flagged in the original Phase 4 design doc is lower than originally estimated for this stage specifically. Still apply a basic defensive truncation on free-text fields (`projects.instructions`, profile text fields) as hygiene, not a full trimming system.

## 6. Generation Engine integration

1. New server action `generateStrategyBrief(projectId)` — lives outside `lib/generation/engine.ts` (keeps the engine SEO-agnostic, per its design). This is the first real caller of the engine beyond the Phase 4.2 test harness.
2. Role-gated (team_lead/seo_manager only, via `assertCanRunGenerations()`).
3. `startGeneration({ projectId, type: 'brief_generate' })`. On `already_active`, return early — no LLM call, matches D2.
4. Gather inputs (§1), build prompt (§4), call Claude (§5).
5. Write raw response to Storage → `output_ref`.
6. `recordProviderCompleted(...)` (new function, §0.1).
7. Parse/validate response (§7). Deterministic `brief_topics` derivation (§2B, §0.2).
8. Persist artifact (§3).
9. `recordArtifactPersisted(...)` then `completeGeneration(...)` (§0.1).
10. `transitionGenerationState(projectId, 'brief_completed', ...)` (exact target state per the existing `generation_state` enum) **and** advance `projects.status` (§0.6) — both required, neither automatic.
11. On any failure after `startGeneration`: `failGeneration(...)` with an `error` object reflecting where it failed (provider call vs parse vs persist), matching the existing `error.type`/`retryable` shape.

## 7. Validation

- Schema validation on Claude's structured output via Zod (already a project dependency), even though tool-use constrains the shape reasonably well — defensive, not trusting the provider blindly.
- **Em-dash check applied to Brief's own generated text fields** (`title`, `h1`, `meta_description`, `unique_value`, `serp_interpretation`, etc.) before persisting — not deferred to the Content/QA stage, since these fields are shown to and can be copied by users immediately on Brief approval. A violation is treated as a failed generation (`failGeneration`, retryable), not silently persisted.
- `brief_internal_links.target_url` values are validated against the actual `website_urls`/`internal_link_candidates` rows supplied in context — anything not present in the supplied set is stripped, not trusted (§0.3).
- No topic-precedence validation here — that's resolved once, at research-upload time (Phase 3); Brief just reads `projects.primary_topic` as already-authoritative.

## 8. Regeneration behavior

- "Regenerate" creates a new `brief_versions` row (`version+1`) and a new `generation_runs` row (`type='brief_generate'`). This is a **new logical generation**, not a retry: `attempt_number=1`, `retry_of_generation_run=null`, since the prior generation succeeded. `attempt_number`/`retry_of_generation_run` are reserved for retrying a *failed* run of the same logical attempt (per D7), not for a deliberate regenerate of already-completed content.
- `content_briefs.current_version_id` flips to the new version on success; the old version is preserved, unchanged, always retrievable.
- **Resolved — see L1/L3.** Regeneration is allowed after approval. The path is: approved Brief → "Request changes" (→ `needs_revision`) → user edits inputs/instructions → "Regenerate" (→ new `draft` version). Regeneration is never triggered directly from an `approved` state without first passing through `needs_revision`. Every regeneration, whether sourced from a draft or a previously-approved version, always creates a new `brief_versions` row at `version+1`, `status='draft'`, requiring its own separate approval; the version it was regenerated from — approved or not — is never mutated and remains permanently retrievable.

## 9. Failure/recovery behavior

Reuses the Phase 4.2 engine as-is (validates the "generic engine, no SEO logic" design goal):
- `queued`/`running` stuck with no `output_ref` → `recoverGeneration` marks `failed`, retryable.
- `provider_completed` stuck (response received, not yet persisted) → `recoverGeneration` currently returns `needs_persist` and stops there by design (persistence is stage-specific). Phase 4.3 needs a **stage-level repair path**: a function in the Brief stage module (not the engine) that reads `output_ref` from Storage, re-attempts parse + persist (§7, §3), and calls `recordArtifactPersisted`/`completeGeneration` itself. This repair path is new code for this phase, living alongside `generateStrategyBrief`, not inside `engine.ts`.
- `artifact_persisted` stuck → `recoverGeneration`'s existing mechanical flip to `completed` already handles this; no new logic needed once §0.1's refactor lands.

## 10. Telemetry fields

Full D7 field set, populated across the two engine calls introduced in §0.1:
`provider`, `model`, `provider_request_id`, `input_tokens`, `output_tokens`, `total_tokens`, `estimated_cost_usd`, `finish_reason` → captured at `recordProviderCompleted`.
`started_at` → `startGeneration`. `provider_completed_at` → `recordProviderCompleted`. `artifact_persisted_at` → `recordArtifactPersisted`. `completed_at`, `duration_ms` → `completeGeneration`.
`attempt_number`, `retry_of_generation_run` → `startGeneration`, per §8's clarified semantics.
`metadata` (jsonb) → stage-specific overflow, e.g. counts of research sources used, whether internal links were available.

## 12. RLS requirements

New migration required (blocking, per §0.5) for `content_briefs`, `brief_versions`, `brief_topics`, `brief_internal_links`:
- SELECT: via `can_access_project(project_id)`. For `brief_topics`/`brief_internal_links`, which only carry `brief_version_id`, this requires the same join-through-parent pattern already used for `research_sources`/`website_urls` (resolve `project_id` via a join to `brief_versions`, or a `SECURITY DEFINER` helper if a plain policy subquery isn't sufficient — no new helper function should be needed, reuse `can_access_project`).
- INSERT/UPDATE: gated to `current_app_role() in ('team_lead','seo_manager')`, consistent with the existing permission matrix (Content Writer cannot generate or approve a Brief).
- No new `SECURITY DEFINER` functions — reuses `can_access_project`/`current_app_role`, so no repeat of the Phase 3 recursion bug class.
- `generation_runs` already has policies from Phase 4.2; `type='brief_generate'` rows need no schema change there.

## 13. Security

- API key: server-only (`lib/ai/client.ts` already uses `server-only`), read from `.env.local`, never logged/printed/committed/exposed in diagnostics — explicit constraint for this entire phase, including any debugging output added during implementation (no `console.log` of request config/headers).
- Prompt injection: research content and `projects.instructions` are externally/user-sourced text — delimited and explicitly framed as reference data, not instructions, in the system prompt (§4). This is the first real implementation of a mitigation the original Phase 4 design doc only described.
- Role enforcement: generation and approval both restricted to team_lead/seo_manager, matching the existing permission matrix.

---

## 14. Token/context limits

- No streaming (locked, D6).
- Current real research payload is lightweight (metadata only, confirmed via the parser's actual field set) — context size is low-risk for this stage today. Basic truncation on free-text inputs as hygiene, not a dedicated trimming system, since there's no evidence yet that one is needed.

- Section-level regeneration (Brief has no sections; that's Content-only).

- Renaming `brief_versions.model_id` for consistency with `generation_runs.model` (§0.7) — cosmetic, not blocking.
